# Qwen3.8 / GLM-5.3 on an EPYC 7F32 + 3× RX 7900 XTX box — placement measurements (2026-09-04)

Lab record, same spirit as the rest of this directory: what was measured, how,
and what it decided. Harness sources are next to this file
(`rome_cpubench.c`, `rome_vkbench.c`, `rome_fp8test.c`, one-file harnesses,
build lines in their headers); they hardcode
Qwen3.8 shapes and build against `quant.h` / `backend_vulkan.o`.

## The machine

| | |
|---|---|
| CPU | AMD EPYC 7F32, 8 cores / 16 threads, Zen 2 (AVX2+FMA+F16C, **no AVX-512**), 128 MB L3. SMT siblings are `i` and `i+8`. |
| RAM | 8 × 32 GB DDR4-2400. Measured read bandwidth 18.8 / 35.7 / 57.1 / 70.9 / 91.6 GB/s at 1 / 2 / 4 / 8 / 16 threads. |
| GPUs | 3 × Radeon RX 7900 XTX (gfx1100, RDNA3), 24 GB each, RADV (Mesa 26.0.8, Vulkan 1.4). Cooperative matrix and int8 dot product are exposed; **no FP8 in hardware**, `fmt=8` is emulated in the shader. |
| Disk | one NVMe. Both checkpoints (Qwen 173 GiB FP8, GLM 182 GiB int4) fit in the 247 GB page cache one at a time, not together. |

The one fact that reshapes every prior number in this repository: on this box
**the disk is not the wall** once a checkpoint is in the page cache. Every
"expert streaming is disk-bound" assumption in `docs/` is about 25–128 GB
machines.

## Baselines (before any change on this branch)

Prompt: 48 tokens, greedy, 64 new tokens, expert cap 512, page cache warm
(`fincore` checked), `COLI_TIMERS=1`.

| Qwen3.8 CPU 16 thr, cap 512 | 1.40–1.51 tok/s | 13.4–17.5 s | routed 383–395, resident 156–162, deltanet 120 |
| Qwen3.8 `qwen38-vk`, 3 GPUs, lazy tier | 1.57 tok/s (128 tok) | 18.8 s | routed 125, resident 196 (!), untimed uploads |
| GLM-5.3 `glm53` Vulkan, 3 GPUs (1296+1695+1695 preloaded from `.glm53_explain.bin`), **8 threads** | **3.17 tok/s** | 60 tok | reproduces the 3.16–3.26 tok/s recorded in the Sep 2 commits (f4fbc4c…573871f) |
| same, 16 threads bound | 2.78 tok/s | | the launcher pins engines to physical cores; 16 threads fight the RADV threads |
| same, 16 threads unbound | 2.02 tok/s | | |
| GLM-5.3 `glm53` CPU-only, 8 threads | 1.97 tok/s | | matches the 1.97–1.98 in the Sep 3 commits |

(For scale: the owner's llama.cpp HIP build of the same GLM checkpoint does
3.15 tok/s on this box with 18 layers offloaded.)

A first GLM measurement in this session read 1.41 tok/s and was wrong three
ways at once: 16 unbound threads, a page cache just evicted by warming Qwen
(167k major faults), and the 6,218-entry `.glm53_usage.bin` histogram that
left the third GPU empty. A bisect of the Sep 3 Vulkan commits at equal
conditions (573871f 2.02, 6da3910 2.07, both 16 threads) showed **no code
regression**: the shader's fmt=8 branch and the dev2/dev3 upload changes cost
GLM nothing measurable. Two operational lessons: GLM's dev2/dev3 preload
loops stop on a count cap only (`COLI_VK_EXPERTS2/3`), so an unlimited cap
spills the tier into host memory (6,458 "resident" experts = 91 GB, evicting
the page cache); and never run a foreign-branch `glm53` on this box
(`eabeb9a`'s cache sizing takes MemAvailable and OOM-thrashed the machine
for 25 minutes).

**Qwen** is where the GPU tier underdelivered: as found it was +8% over the
CPU fresh-process (1.57 vs 1.45) and +27% in steady state per the Sep 3
commits (5.0 vs 3.9, run 2 of 3 through the persistent server at 8 threads),
against a 3× per-expert advantage in the microbenchmarks. The reason is not
the GPU: see the per-op numbers.

## Where the Qwen CPU token went (perf, flat, 16 threads)

```
22.9% + 20.0%  libgomp barrier spin      <- 15 threads waiting for 1
22.5%          matmul_fp8 (routed experts)
18.1%          q38_matmul_bf16 (dense)
 3.6%          kernel spinlock (page-table lock under concurrent faults)
```

The waiting was page faults: an expert served from the file mapping is bound
by pointer (no copy) and first touched inside the 16-thread matmul; the thread
that faults (minor with a page-table lock, or major to NVMe after eviction)
stalls the other fifteen at the region barrier. Isolated, the same FP8 kernel
ran 4–6× faster than inside the engine (0.20 vs 0.8–1.1 ms per expert).

## Per-op placement matrix (Qwen3.8 shapes, this box)

CPU: real engine kernels, weights rotated through pools larger than L3.
GPU: real `backend_vulkan.o` through its public API, distinct-expert pools
larger than Infinity Cache, times include submit+fence round trip.

| op | shape | CPU (best) | GPU dev0 Vulkan | verdict |
|---|---|---:|---:|---|
| submit + fence round trip | tiny matmul | — | **53–66 µs** | the engine's comment says 0.4 ms; here it is 7× cheaper, so per-layer submits are affordable |
| BF16 dense GEMV | 2560→10240 | 0.52–0.57 ms, 92–101 GB/s (DRAM-bound) | no BF16 shader; int8 proxy 0.198 ms (132 GB/s eff.), fp8-emul 0.342 ms | CPU is at its bandwidth floor. GPU int8 is 2.9× faster per call but needs a numerics change or a new BF16 `fmt`; per token this is 8.5 GB → ~85 ms CPU floor vs ~50 ms GPU incl. ~48×5 submits |
| BF16 dense GEMV | 6144→2560 | 0.32 ms, 99 GB/s | int8 0.171 ms, int4 0.147, fp8 0.295 | as above |
| LM head | 2560→248320 | 12.3 ms, 104 GB/s | int8 1.58 ms (403 GB/s), int4 1.36 ms | GPU wins 8× **if** the head is int8/int4; kept on CPU for numerics |
| BF16 dense, prefill S=32 | 2560→10240 | engine kernel 9.0 ms (187 GFLOP/s); 4-accumulator variant 5.1 ms (330 GFLOP/s) | — | a 1.8× CPU prefill kernel win is available (not landed: prefill is dominated by expert reads) |
| int8 dense GEMV (AVX2 `maddubs`) | 2560→10240 | 0.27 ms, 99 GB/s | — | int8 dense on the CPU would halve the dense floor; changes numerics, not done |
| routed experts, decode (10 experts) | 2560→640 ×2, 640→2560, FP8 | engine kernel 2.0 ms/layer = **96 ms/token** (24.6 GB/s, ALU-bound); F16C decode **70 ms/token** (33.9 GB/s) | fp8-emul group 0.467 ms/layer = **22 ms/token**; int8 13.5 ms; int4 12.6 ms | GPU wins 3× per expert **when resident**; VRAM holds ~14k of 24.6k experts |
| routed experts, prefill rows=8 | same | — | fp8 1.66 ms/layer (0.166 ms/expert), int8 1.11 | FP8 emulation costs 1.5× vs int8 on the GPU: real, but not decisive |
| 3 GPUs, one expert group each | K=10 per device | — | sequential (engine as found) **2.37 ms/layer = 114 ms/token**; concurrent issue/take **0.63 ms = 30 ms/token** | the found engine serialised the three GPUs |
| 4 dense tensors, one submit vs four | I=2560 | — | 0.247 vs 0.378 ms | batching dense dispatches pays even at 55 µs/submit |

**The precision↔WMMA hypothesis** from the handoff: partly right, mostly
moot for decode. FP8 emulation makes the GPU expert GEMV 1.7× slower than
int8 at the same bytes (0.467 vs 0.282 ms per 10-expert group), but decode is
a GEMV, so cooperative-matrix hardware never enters; the emulated FP8 path is
still 3× faster per expert than the CPU. Converting Qwen experts to int8/int4
would buy ~9 ms/token on the GPU and halve the VRAM per expert (twice the
resident tier), at the cost of a second copy of the checkpoint and a
numerics change. Worth doing for VRAM, not for WMMA.

**Why the Qwen tier gained so little** (measured, not inferred): (1) the
CPU expert path was 4–6× slower than its own kernel because of page-fault
stalls, and the GPU path still ran that CPU path for every non-resident
expert; (2) the three GPUs were driven sequentially (114 ms/token at full
residency); (3) the tier filled lazily, so 4.7 MB uploads landed inside
decode, and the driver's spin-wait threads took cores away from the dense
matmuls (resident BF16 149 → 196 ms). None of that is RDNA3's fault.

Two follow-ups measured and **rejected** (code removed, not shipped as knobs):

| tried | Qwen CPU | why it lost |
|---|---:|---|
| `num_threads(8)` on the FP8 kernel inside the 16-thread pool (threads 0–7 = 8 distinct cores, siblings are `i`/`i+8`) | 1.70 tok/s vs 1.90 | the eight idle pool threads spin on the sibling hyperthreads and slow the eight that work (resident BF16 125 → 166 ms too). Only a genuinely 8-thread pool helps. |
| two FMA chains per 128-block | 1.68 / 1.90 at 8 / 16 threads: no change | the kernel is not FMA-latency-bound; logits differed from the single chain by 8e-6 (argmax same) for nothing |

Numerical identity, last-token logits after the same 64 greedy tokens,
against the pristine binary: prefault + F16C + fused dense **max abs diff 0**
(bit-identical); `qwen38-vk` 3-GPU path max abs diff 7.6e-6, cosine 1.0,
same argmax (the GPU FP8 dot products accumulate in a different order).

Routing history matters for the tier: after the benchmark runs grew
`.coli_usage` from 9,396 to 11,244 nonzero experts, the same 3-GPU 128-token
run went from 2.99 to **3.38–3.39 tok/s** (TTFT 8.5 s).

Final numbers with the committed tree (same prompt, cap 512):

| configuration | decode | routed | resident BF16 | expert-read |
|---|---:|---:|---:|---:|
| `qwen38`, 16 threads | 2.00 tok/s (64 tok) | 221 ms | 127 ms | 41 ms |
| `qwen38`, `OMP_NUM_THREADS=8 OMP_PLACES=cores OMP_PROC_BIND=close` | 2.28 tok/s (64 tok) | 143 ms | 145 ms | 57 ms |
| `qwen38-vk`, 3 GPUs, 16 threads | 3.38 tok/s (128 tok) | 70 ms | 133 ms | 64 ms |
| `qwen38-vk`, 3 GPUs, **8 threads one per core** | **4.05 tok/s** (128 tok) | 60 ms | 114 ms | 27 ms |

The last row is the recommended launch on this box: 2.8× the pristine CPU
engine, 2.6× the pristine `qwen38-vk`. With the GPUs doing the experts, the
CPU's job is the dense BF16 stream, and eight threads leave the RADV
submit/fence threads their own hyperthreads instead of fighting sixteen
spinners for them (resident 133 → 114 ms). Both `qwen38` rows are
bit-identical to the pristine binary on last-token logits; the 3-GPU path
was checked at 64 tokens (max abs 7.6e-6, same argmax) — a 128-token dump is
a different position and is not comparable, which is why no 128-token
identity figure is quoted.

## Steady state: the regime the server runs in (`tools/datapoint.py`, 8 threads)

Persistent `SERVE=1` engine, page cache evicted before load, 80 completion
tokens, expert cap 512; one cold request, the same prompt twice (upper
bound), then two different prompts (the tool's primary serving result).
`datapoint.py` sets `OMP_NUM_THREADS` to physical cores, as the `coli`
launcher does, so these are 8-thread numbers, and the pristine rows match the
3.9 / 5.0 tok/s in the Sep 3 commit messages.

| engine | warm-identical (upper bound) | rotating prompts, median | cold first request | cold TTFT |
|---|---:|---:|---:|---:|
| pristine `qwen38` (CPU) | 4.11 tok/s | 2.87 | 2.54 | 19.5 s |
| patched `qwen38` (CPU) | **4.70** (+14%) | 2.89 (±0) | 2.47 | 11.9 s |
| pristine `qwen38-vk`, 3 GPUs | 5.34 | 2.72 | 2.08 | 18.3 s |
| patched `qwen38-vk`, 3 GPUs | 5.35 (±0) | **3.69** (+36%) | **3.59** (+73%) | 7.1 s |

Read against the fresh-process numbers above: the pristine engine was never
1.45 tok/s in service, only in a fresh process that pays every first-touch
fault. In steady state the branch buys +14% on the CPU path, nothing on the
GPU upper bound (the lazy tier had already filled and hits 100% on a repeated
prompt), +36% on changing prompts, and a much better first request (the
preload of 14,673 experts costs 90 s at load, then pays back on every cold
request: 7 s TTFT instead of 18). The rotating-prompt CPU number did not move:
prefaulting relocates the first-touch cost of new experts, it does not remove
it, which is the case for populating the whole mapping at load (backlog 3).

## What the data killed

- **"VRAM-reside Qwen's dense/attention/shared-expert weights" as the first
  move** (the prior audit's #1). It is real (~85 ms/token CPU floor vs ~50 ms
  on the GPU) but third in line behind the two 100+ ms items above, needs a
  BF16 shader format or an int8 conversion, and competes with experts for the
  same 72 GB. Now evidence-ranked, not killed.
- **"GPU loses to CPU because RDNA3 lacks FP8"**: emulation costs 1.7× on the
  GPU, the GPU still wins 3× per resident expert.
- **AVX-512 / VNNI ideas**: not on this silicon.
- **Bigger expert cap as a footgun fix** (`cap=1` default): on this box the
  mmap path makes a miss a pointer bind, so cap only changes hit telemetry and
  the batch loader's willingness to prefault; 512 is right here.

## Backlog, ranked by measured delta per token (Qwen, from the 2.99 tok/s state ≈ 334 ms)

1. **Dense set off DRAM** (resident BF16 137 ms + shared 19 ms): int8 on the
   GPU measured 132–400 GB/s effective vs 100 GB/s CPU; ~5 submits/layer ×
   48 × 55 µs = 13 ms. Expect −80 to −100 ms. Needs a BF16 `fmt` in
   `qmatmul.comp` (numerics-preserving) or an int8 dense conversion, and the
   DeltaNet/QSA cores stay on the CPU with per-layer round trips.
2. **Expert-read 71 ms (`MADV_POPULATE_READ` cost of first-touch CPU misses)**:
   goes to zero in steady state; for cold sessions, populate at load (whole
   mapping, 173 GiB fits) behind a knob.
3. **MTP speculative decoding** (tech report, Table 4: mean accepted length
   4.06 with four-step MTP reusing QSA indices). On a bandwidth-bound decode
   the dense 8.5 GB is read once per verify step, experts ~4×: ≈ 2.4× tokens
   per second at equal bytes. Largest multiplier available; largest effort
   (MTP module weights, index reuse, verify path).
4. **More routing history for the preload**: only 9,396 experts had nonzero
   counts; VRAM has room for ~14,000. Longer/rotating usage capture fills it.
5. **CPU prefill kernel** (4-accumulator BF16, 1.8× on S=32) and GPU prefill
   for resident experts: TTFT, not decode.
6. **GLM-5.3**: 3.17 tok/s on the tier at 8 threads equals llama.cpp HIP's
   3.15. CPU-side items are the scalar KDA inner loop and the O(context²)
   pooled-key recompute in `sparse_index.h`; the mmap expert path likely
   carries the same first-touch fault stall as Qwen's did (not measured).

On cache state: the harness's own `echo 3 | sudo tee /proc/sys/vm/drop_caches`
needs interactive sudo on this box, so it warns and continues. That turns out

## G1: prefault at bind and populate-at-load, ported to GLM — both regress, both shipped off

`glm53_populate_range()` is a straight port of `qwen38_core.h`'s
`q38_populate_range` (same `MADV_POPULATE_READ` call, page-aligned, advisory)
into `glm53.c`'s `expert_read` mmap fast path — the analogous per-bind
prefault — plus a second call site in `expert_map_init` that faults an
entire shard file at load instead of per-expert (the "populate-whole-mapping"
half of G1, which does not exist yet on the Qwen side either — that is
roadmap item Q0, still open — so this is a first implementation of the idea,
not a literal port of existing Qwen code).

**Oracle, both knobs, against the pristine binary** (CPU-only, same prompt,
`--logits`, so GPU residency cannot be a confound): `teacher_forcing`
bit-identical, `last_logits` max abs diff 0, cosine 1.0000000000, same
argmax. This only ever changes *when* a page faults, never what gets read,
so bit-identity is expected and confirms nothing in the read path moved.

**Performance, prefault at bind (`GLM53_MMAP_POPULATE`), through
`rome_bench.sh` against G0's exact config:**

| config | rotating median | cold decode |
|---|---:|---:|
| G0 (lazy fault) | 1.65–1.66 tok/s | 1.23–1.25 tok/s |
| prefault ON (2 runs) | 1.48, 1.48 tok/s | 0.98, 0.99 tok/s |
| prefault OFF, re-confirmed | 1.64 tok/s | 1.27 tok/s |

**Regression, not a gain** — the opposite of Qwen's 4–6× win from the same
primitive — and it reproduces: two runs at 1.48 each, and toggling only this
one env var with everything else fixed (same histogram copy, same cap,
same prompt suite) reproduces G0 when off and the regression when on. Root
cause was not profiled at the time (out of scope for a port), and two
hypotheses were guessed here: higher call frequency, or `mmap_lock`
contention between eight concurrent `madvise` callers.

> **Both guesses were wrong — see the G1b section below**, which instrumented
> it. The dominant cost was prefaulting experts that the GPU then serves from
> VRAM, whose host pages are never read (32% of binds). Contention was
> measured and ruled out. The paragraph above is left as written for the
> record; do not carry its hypotheses forward as findings.

**Performance, populate-whole-mapping-at-load (`GLM53_POPULATE_LOAD`):**
engine load 122.59 s (vs the usual ~9–10 s single-digit-second load — this
is the entire 182 GiB checkpoint being fault-in at once), for a rotating
median of 1.62 tok/s and cold TTFT of 17.66 s — both within G0's own
run-to-run noise (1.65–1.66, 17.48–17.93 s). **Correct, but no measured
benefit against a large, certain cost**: over 110 s of extra load latency
bought nothing detectable on either the metric it targets (cold TTFT) or
the primary one (rotating median). Not recommended as built; the request
mix here touches at most a few dozen of the checkpoint's 12,096 experts per
call, so eagerly faulting all of it may simply be solving a problem this
workload doesn't have at this scale.

**Shipped:** both knobs land as opt-in, default OFF — `GLM53_MMAP_POPULATE=1`
and `GLM53_POPULATE_LOAD=1` respectively, neither on by default. This is the
opposite default from Qwen's `Q38_MMAP_POPULATE` (default on there because it
measured a win); shipping GLM's version on by default would ship a regression
as the production default, which nothing in CLAUDE.md's discipline permits
without a favorable measurement.

**Gate ("teacher_forcing identical; rotating median and cold TTFT vs G0"):
met** — the oracle passed and both figures are measured against G0. The
Sonnet-tier premise for this item — "the design already exists in the repo,
the model copies and measures" — held for the mechanics (the primitive
ported cleanly, compiled clean, stayed numerically safe) but not for the
*expected direction* of the result: the pattern that worked for Qwen does
not transfer to GLM's access pattern. That is itself the measured answer G1
asked for.

## G1b: why the prefault regressed — measured, and it is not either hypothesis

G1 shipped its prefault off with two guesses on record (call frequency,
`mmap_lock` contention) and neither tested. Both are now tested. The answer is
a third thing, and the mechanism is fully quantified.

Instrumented `glm53_populate_range` with a per-call timer, a byte counter and
a bind classifier, reported through the existing `[PROF]` destructor. Fresh
process, 3 GPUs, same histogram copy, 32 greedy tokens, 8 threads:

| config | decode | populate calls | time in `madvise` | bytes advised | CPU expert compute |
|---|---:|---:|---:|---:|---:|
| prefault all (G1 as measured) | 2.410 tok/s | 60,684 | 14.394 thread-s | 143.41 GB | 3.393 s |
| prefault CPU-only (G1b fix) | 3.006 tok/s | 41,412 | 7.533 thread-s | 97.87 GB | 3.080 s |
| **prefault off (shipped)** | **3.222 tok/s** | 0 | 0 | 0 | 3.841 s |

**What it actually was.** `expert_read` binds an expert's slot
unconditionally, and `expert_mats` builds its views, *before* the MoE loop
decides whether to serve that expert from VRAM. For a GPU-resident expert the
host pages are then never touched at all — it is served from its
`vk_reg_at` tensors. The prefault was faulting in the full ~14 MB slot for
those anyway: **3,212 of 10,114 binds (32%), about 46 GB per 32-token
decode, for bytes nothing ever reads.** Skipping them is the fix, and it
recovers most of the regression (2.410 → 3.006 tok/s).

Two supporting facts from the same instrumentation. `contig=0`: **no expert
in this checkpoint is contiguous**, so every bind takes the six-`madvise`
path and the `ref->contig` single-call branch G1 wrote never once executes.
And the six pieces are ~2.36 MB each, so cost tracks bytes at roughly
0.3–0.4 µs per 4 KB page.

**Both original hypotheses are wrong, and one is disproved outright.** Call
frequency is a contributing factor only (6 calls/bind, a third of them
pointless) — fixing the pointless third left the primitive still net
negative. `mmap_lock` contention is **ruled out**: 172.2 µs/call at
`OMP_NUM_THREADS=1` against 181.9 µs/call at 8 threads. If concurrent
`madvise` were serializing on the mapping's lock, the single-threaded number
would be far lower. It is the same, so this is real page-table work, not
waiting.

**Why it still loses after the fix.** The mechanism does what it was designed
to do — it genuinely moves faults out of the matmul, CPU expert compute drops
3.841 → 3.080 s. It just spends 7.5 thread-seconds of `madvise` to save 0.76
thread-seconds of matmul: a ~10:1 losing trade. Eager population pays for
every page of the slot up front in a blocking syscall; the lazy path pays only
for what the arithmetic reaches, interleaved with the arithmetic.

**Kept, not removed** — deliberately against this record's own
"measured and rejected → code removed" precedent, for one reason: every fault
counted above is a *minor* fault, because this box holds the whole 182 GiB
checkpoint in page cache. That is this machine's defining and *unrepresentative*
property (see the top of this file). On a RAM-constrained box — the actual
deployment target for this work — those same first touches are major faults to
NVMe taken *inside* the matmul, which is precisely the stall Qwen's prefault
was built to remove. The sign of this knob is hardware-dependent and this rig
is the case where it loses. It stays `GLM53_MMAP_POPULATE=1`, off by default,
now strictly better than G1's version wherever it is switched on. Anyone
enabling it on a smaller box should re-measure there rather than trust either
number here.

The `[PROF]` instrumentation is permanent and free: the persistent-engine
rotating median with the knob off is 1.71 tok/s, matching G2's 1.71/1.69
exactly. It is GLM's first per-op visibility into the expert path
(mmap serve/copy, GPU vs CPU binds, populate cost) and feeds G3.

## G2: dev0/dev2/dev3 were sequential — issue-all/take-all fixes it, small real gain

**Check, first** (the roadmap's own first step): yes, sequential. GLM's MoE
dispatch called the three devices' *synchronous* forms back to back —
`coli_vk_expert_group` (dev0), `coli_vk_expert_group2` (dev2),
`coli_vk_expert_group3` (dev3) — each one submit-and-wait
(`coli_vk_expert_group` is `eg_prepare_submit` immediately followed by
`coli_vk_expert_group_take`, per `backend_vulkan.c`), so dev2's submit could
not start until dev0's fence had already signalled. The async `_issue`/`_take`
pair for all three devices already existed in `backend_vulkan.c` — built for
Qwen's `q38_moe_decode` — untouched and unused by `glm53.c` until now.

**Fix:** replaced the three sequential submit-and-wait loops with a
round-based issue-all-three/take-all-three loop (each device still chunks at
64 items per call — the descriptor-pool size `eg_prepare_submit` allocates
once — so a device needing more than one chunk still serializes against
itself across rounds; only same-round chunks across the three devices
overlap). The one invariant that had to hold under partial failure: a group
that was successfully issued is always taken before the loop can advance or
exit, win or lose, so a mid-round failure on one device can never leave
another device's single in-flight slot stuck for the next call.

**Oracle**, 3 GPUs, same resident set both runs (dev0 1296 heat-ranked, dev2
1695, dev3 1695 — verified identical via the preload lines before comparing):
pristine vs patched output files are **byte-for-byte identical** (`diff`
reports no difference at all — teacher_forcing and last_logits both, the
strongest form of this check).

**Performance**, through `rome_bench.sh` against G0:

| config | rotating median | cold decode |
|---|---:|---:|
| G0 | 1.65–1.66 tok/s | 1.23–1.25 tok/s |
| G2 (2 runs) | 1.71, 1.69 tok/s | 1.25, 1.27 tok/s |

A real, reproducible gain — every one of the four rotating requests improved
in both runs (1.63/1.63/1.79/1.80 and 1.63/1.63/1.76/1.82, against G0's
1.59/1.58/1.72/1.72) — but a modest one, roughly +3–4% on the headline, not
the 73% (2.37→0.63 ms/layer) Qwen measured from the identical restructuring.
Per-op timing to attribute this precisely (e.g. an `[VK_PROF]` or `[PROF]`
breakdown isolating the expert-group phase) was not pursued here — profiling
and its interpretation is Opus-tier (G3), and the direct before/after
tok/s answers this item's gate on its own. A plausible reason the win is
smaller than Qwen's, unconfirmed: GLM's per-token GPU-resident expert count
is usually small (topk routed across three devices), so each device's group
here is often just 1–2 experts — the three submits were already short, and
serializing three short things costs less than serializing three that are
individually larger, as Qwen's groups were.

Shipped unconditionally, no env knob — same choice as Qwen's version of this
fix: a pure concurrency reordering with an oracle-clean, no-regression
measurement doesn't need one.

**Gate ("teacher_forcing identical; tok/s vs G0"): met.** Unlike G1, this
port's expected direction held: the pattern that helped Qwen also helps GLM,
just by less.

### KDA, decomposed (2.30 ms/call, single thread)

State is 64 heads × 128 × 128 floats = 4 MB per layer, 136 MB across 34
layers; each token streams it twice, read and write, and it is cold from
DRAM every time because ~112 MB of expert weights pass through the caches
between visits to the same layer. That is 16 MB of traffic per call —
**0.9 ms at one core's measured 18.8 GB/s.** Then ~57k transcendental calls
per layer (`expf(alog[h])` recomputed 8,192 times per token though it has 64
distinct values; SiLU on 24,576 conv channels; the decay sigmoid on 8,192;
`expf` per k in the recurrence) ≈ **1 ms**, and 24,576 twelve-byte
`memmove`s per layer to shift the conv window (2.06% of all cycles) ≈
**0.4 ms**. 0.9 + 1 + 0.4 ≈ 2.3. The model closes.

Two of the roadmap's premises are wrong and one is moot. *"KDA ≈ 110 ms of
a 300 ms token":* it is 78 of 373, 21% not 37%, and third behind the CPU
expert kernel and (at this context) not far ahead of MLA. *"AVX2 vectorize
the scalar inner loop":* GCC's own `-fopt-info-vec` report shows both `for v`
passes in `coli_kda_step` already vectorized with 32-byte vectors; what it
cannot vectorize is the `expf` calls. *"per token × head × position over
L=512":* that loop is `mla_layer`'s absorbed-attention dot product over
`kv_lora = 512` — the roadmap describes MLA's inner loop and attributes it to
KDA. And *"KDA is bandwidth-bound, move it to the GPU":* at 2.3 ms against a
0.9 ms single-core floor and a 0.23 ms 8-core floor, it is not.

### The decision (the Fable gate after G3): CPU, not a shader

Parallelize `coli_kda_step` across its 64 independent heads (per-thread
`memory` scratch), hoist `expf(alog[h])` to once per head, and parallelize
the conv pass across its channels so the per-channel `memmove` spreads
eight ways. Not a ring index: `kda_window` is exported as a raw segment-
migration span, and a position counter would change its meaning. Expected
2.30 → ~0.35–0.45 ms/call, **78 → ~12 ms/token**, **bit-identical** (per-head
arithmetic order unchanged; the hoisted `expf` computes the same value once).
`delta_attention.h` turns out to be included by `glm53.c` alone — `kimi_k3`
has its own `kda_forward` — so there is no sibling oracle, only a rebuild. A GPU recurrence shader — none exists in
`backend_vulkan.c`; it is from-scratch — would floor at ~0.15–0.2 ms/call
(16 MB over VRAM bandwidth plus two ~55 µs submits, state resident in 136 MB
of VRAM), about 9 ms/token better than the CPU plan, for 2–4 days and a new
numerics path. Not now. The one-page spec with the oracle is
`G4-KDA-SPEC-2026-09-04.md`, next to this file.

## G4: KDA parallelised — +7% serving, and the spec's floor was wrong

Executed `G4-KDA-SPEC-2026-09-04.md` in three commits. Result: **rotating
median 1.84 / 1.83 tok/s against G2's 1.69–1.71 (+7–8%)**, everything
bit-identical. The spec's per-call gate was not met, and the reason is a
mistake in G3's decomposition that only a sub-timer could find.

| step | change | `[OPTIME] kda` ms/call | oracle |
|---|---|---:|---|
| — | G3 baseline | 2.301 | — |
| 1 | `expf(A_log[h])` hoisted out of the `d` loop (8,192 → 64 calls/token) | 2.249 | bit-identical |
| 2 | 64 heads in parallel, per-thread `memory` scratch | 2.207 | bit-identical |
| 3 | 24,576 conv channels in parallel | **1.598** | bit-identical |

**Step 2 fired the stop condition and that was the point.** Parallelising
the heads — the spec's centrepiece, predicted to reach ~0.5 ms/call — moved
2%. The ROADMAP said to stop there and re-examine rather than pile on more
parallelism, so `kda_layer` was sub-timed (8 threads, greedy 32):

| part | 8 threads | 1 thread | scales? |
|---|---:|---:|---|
| projections (8 matrices, one GPU submit) | 0.660 ms | 0.886 | 1.3× |
| decay | 0.062 | 0.061 | no |
| `coli_kda_step` | 1.031 | 1.060 | **no — 3%** |
| output norm | 0.064 | 0.063 | no |
| `ko` (one more GPU matvec) | 0.400 | 0.489 | 1.2× |

Two errors in §G3 show up here. First, `coli_kda_step` was flat under head
parallelism because its *other* loop — 3·width = 24,576 conv channels, one
`expf` each — was still serial; step 3 took that 1.031 → 0.378 ms (2.7×),
and it, not the head loop, is where KDA's CPU time lived. Second and larger:
**projections + `ko` are 1.05 ms, ~47% of the original 2.22, and they are GPU
submit round trips** — two per token per layer, 9 matrices, ~55–66 µs each
plus the matvecs. §G3 decomposed KDA as 0.9 ms DRAM + 1.0 transcendentals +
0.4 memmove ≈ 2.3 and got the total right by coincidence while attributing
none of it to the dense projections around the recurrence.

So the spec's gate (≤ 0.6 ms/call) was never reachable by parallelising the
recurrence: **the floor for this approach is ~1.05 ms/call**, and at 1.598
the remaining CPU-side slack is ~0.54 ms (step 0.378 + norm 0.097 + decay
0.060). Halving KDA again needs the *submits* addressed — chaining `ko` into
the same batch as the eight projections would remove one of the two round
trips per layer per token — not more threads.

| g4-run1 | 1.84 tok/s | — | — |

## Long context: the indexer is real, and it is not the long-context problem

G5's gate asked for a DSA-index timer GLM did not have. Added one (`[OPTIME]
mla split`: projections / indexer / attention core), then measured decode at
two context lengths — which is what the ordering of G5 against G8 had been
resting on guesswork for.

| context | proj | **index** | attn | mla total | index per ctx token |
|---:|---:|---:|---:|---:|---:|
| 52 | 1.049 ms | **0.108 ms** | 2.901 ms | 4.060 ms | 2.104 µs |
| 502 | 1.064 ms | **1.050 ms** | 15.534 ms | 17.651 ms | 2.090 µs |

**The indexer is exactly linear per call** — 2.09 µs per token of context,
constant across a 10× range — so it is O(context) per token and O(context²)
per generation. G5's premise is confirmed.

**But the attention core is bounded and the indexer is not**, and that is the
part the roadmap had backwards. From the code: `coli_sparse_index_width()`
returns `topk + pool - 1` = **2051, a constant**, and the attention loop runs
over that width, skipping entries past the end. The pooling loop runs over
`pools = (sequence + pool - 1) / pool`, which grows forever. So:

- `attn` ≈ 1.44 ms + 28.07 µs × min(ctx, 2051) — **flat above ~2k context**
- `index` ≈ 2.09 µs × ctx — **never flattens**

Both are single-threaded. Per token (11 MLA layers), holding the fits:

| context | index ms/token | attn ms/token | index share of MLA |
|---:|---:|---:|---:|
| 2k | 46 | 650 | 7% |
| 8k | 188 | 650 | 22% |
| 16k | 367 | 650 | 36% |
| 32k | 735 | 650 | 53% |

So the indexer only overtakes the attention core somewhere near **27k tokens**
of context. Below that, the biggest long-context cost is `attn` — flat, large,
and single-threaded, which is **G8**, not G5. The roadmap's "the only
O(context²) component" is true and was being read as "the long-context fix";
it is not, at any context anyone is likely to run here.

**This also sets G5's real trigger.** G8 parallelises `attn` across 8 cores
(650 → ~81 ms/token). After that, the indexer is MLA's dominant term above
roughly **3.5k context**, not 27k. G8 first, then G5 — and G5's value is a
function of the context length the deployment actually sees, which is a
product question this record cannot answer.

Caveat on the fits: two points, at 52 and 502 tokens, both below the 2051
cap, so the flattening above it is derived from the code's constant bound and
not yet measured. A run at ~4k would confirm it; the 1.9k and 3.8k runs were
started and stopped because a prefill that long costs more rig time than the
derivation is worth. If `attn` does *not* flatten near 2k, this whole ranking
inverts and G5 moves ahead of G8.

## G7: the router, parallelised — the first leg of the post-G4 road

First item on the road ranked in the record's long-context section. The
288-row MoE router score is a scalar f32 reduction against the current
token, single-threaded; each row is independent (own weight row, own
`score[e]`, no shared accumulator), so `#pragma omp parallel for` on the
expert loop changes nothing about any row's own summation, only the order
rows are computed in.

prefill — silent corruption, not a crash. Fixed by inspection before building.

**bit-identical**.

## G8: MLA's two head loops, parallelised — second leg of the road

The record's own long-context section named MLA's attention core as the
largest single long-context cost (~650 ms/token flat above 2k). Second on
the road for that reason, ahead of G5.

**Checked before writing anything:** `mla_layer`'s two per-head loops (the
absorb projection, and the attention-core softmax+pool+`kvb_v`) already call
`mv_rows` (`quant.h`), which has its own `#pragma omp parallel for` over its
own output rows. Naively wrapping the outer per-head loop would nest one
parallel region inside another — exactly the class of regression already on
record for this box (`num_threads(8)` inside a 16-thread pool, Qwen: 1.70 vs
1.90 tok/s). Rather than assume either way, compiled a 20-line probe with
the exact same `gcc -O3 -fopenmp` flags this codebase uses and measured
`omp_get_max_threads()` inside a nested region directly on the rig:

```
omp_get_nested()            = 0
omp_get_max_active_levels() = 1
threads observed inside the nested region = 1
```

Nesting collapses to one thread per call by default on this box's
GCC/libgomp. Wrapping the outer loop is safe — `mv_rows`'s inner pragma
silently becomes a no-op serial loop when called from inside another
parallel region. This also explains G3's own number: today the code pays
**two tiny OMP team spin-ups per head per token (128 total)**, each barely
using its 8 threads before tearing back down, rather than one team doing
real work across 64 heads at once.

**The absorb loop** was embarrassingly parallel as found — each head writes
its own `absorbed[]` slice, reads its own `queries[]` slice, no shared
mutable state.

**The attention-core loop** had the same trap G4's KDA fix guarded against:
`score[]` and `pooled[]` were single buffers reused across all 64 heads.
Sized per-thread (reusing `coli_kda_threads()` from `delta_attention.h`,
already included, already carrying the `#ifdef _OPENMP` this needs) and
indexed by `omp_get_thread_num()`. A shared slice would have corrupted every
head's softmax while still emitting plausible tokens.

**Oracle**, 3 GPUs, same histogram, teacher_forcing and last_logits by
`diff`, no tolerance: standard prompt and ~700-token prompt both
**bit-identical**.

**`[OPTIME] mla split`**, greedy 128, mean context 88 tokens:

| phase | before | after | |
|---|---:|---:|---|
| proj (absorb) | 1.024 ms | 0.659 ms | 1.55× |
| attn (core) | 3.806 ms | 1.237 ms | 3.08× |

## G9: CPU expert compute overlapped with the in-flight GPU groups — third leg

G2 left this half deliberately deferred: its own record entry above says so.
Third on the road because it falls straight out of G2's sub-split rather
than needing new evidence — G3's `[PROF] eg`/`cpu` numbers already showed
the CPU experts finishing entirely before the GPU groups were issued.

**Mechanism.** In `ffn_layer`'s classify loop, a CPU-only expert's `Mat`
triple (`gate`,`up`,`down`) and `eid` are now saved into a deferred list
instead of being computed immediately. A new helper,
`ffn_moe_run_deferred_cpu`, runs that saved list once, in the gap between
the GPU groups' issue and take (whichever round issues anything first) —
so the CPU compute overlaps the fence wait instead of finishing before it
starts. A catch-all placed right after the dispatch block's closing brace
runs any still-undone deferred experts for a layer where nothing routed
anywhere GPU-resident (so the issue/take block never executed at all).

**Safety, checked before writing anything:** deferring is gated on
`can_defer = g_vk_ready && (n_union <= block)`. The block-based expert
cache exists so a later block's `expert_read` can evict an earlier block's
slots once that block's own experts are consumed — and a deferred CPU
expert's saved `Mat` still points into its slot's weight buffer, so
deferring past the classify loop is only safe if no eviction can happen
between classifying and running it. `n_union <= block` (`cache->cap` is
512 in every measured config; `n_union <= topk*tokens` for decode) means
exactly one block, so there is no later block to evict anything —
decode always qualifies. A smaller cap or a larger prefill batch falls
back to today's immediate-compute path, completely untouched.

**Does not change summation order into `out[]`:** CPU contributions still
land in the same relative order they always did — the order experts first
appear in `union_ids`, still entirely before the GPU dev0/1/2
contributions. Only the wall-clock moment moved, not the arithmetic.

**Oracle**, vs `65d21e2` (G8, the immediately preceding landed commit), 3
GPUs, same histogram, teacher_forcing and last_logits by `diff`, no
tolerance: standard prompt and ~700-token prompt both **bit-identical**.

| before | 2.637 s | 13.612 s | 16.249 s |

## G12: `ko`'s round trip cannot fold into the projections' submit — blocked

Checked before writing anything, per this record's own practice, and the
premise does not survive: G12 as specified ("fold `ko` into the same
batched submit as the eight projections, two round trips become one") is
**not achievable as a Sonnet-tier plumbing change.**

**Why the literal fold is impossible.** `ko`'s input is `normed`, not the
row the eight projections read. `normed` only exists after
`coli_kda_step` (the CPU recurrence) and the per-head norm+gate step run —
both entirely on CPU, both strictly between the projections and `ko`,
within the same token, same layer. Putting `ko` in the same
`vkQueueSubmit` as the projections needs that CPU stage to also run on the
GPU, as a barrier-separated stage in one command buffer — a real compute
shader for the recurrence, not a port of the existing `vk_batch_mv_chain`
pattern.

**Why the G9-style workaround (fold with independent work instead) doesn't
apply either.** G9 worked because the CPU-only experts were provably
independent of the GPU expert groups within the same MoE layer. Checked
whether the same trick applies here — it doesn't, because GLM-5.3 decode is
strictly sequential at both granularities:

- `kda_layer`'s `tokens` parameter is **1 during decode** (confirmed: this
  track's own numbers only reconcile if it is — `[OPTIME] kda`'s ms/call
  divided into ms/token gives ~34 calls per token, matching the KDA layer
  count, not a token batch). There is no "next token" inside one call to
  pipeline `ko(t)` against.
- Each layer's output feeds the next layer's input through the residual
  stream (`coli_hc_post`/`branch`/`next`, `glm53.c` main layer loop) — so
  there is no independent GPU work anywhere else in the same decode step
  to overlap `ko`'s wait with, unlike G9's CPU experts.

**Checked, and ruled out, the one alternative that would have been pure
plumbing:** whether `ko`'s separate dense-matmul call (`coli_vk_matmul`,
the singular path) pays a full descriptor-rebind + command-buffer
re-record cost every call because the interleaved batched-projections path
(`coli_vk_matmul_multi`, which shares `G.cmd`/`G.fence`/`G.dset` and
explicitly invalidates the singular path's cache — `backend_vulkan.c`,
`G.cmd_ready = 0; G.bound_tensor = NULL;` after every multi-batch call, by
design) forces the expensive path every time. A `VK_PROF=1` diagnostic run
confirms this is **not** the cost:

Standard 3-GPU environment, `--greedy 260`, cumulative at n=49152 calls
(aggregate across all non-batched dense calls, not `ko`-isolated, but the
same shared code path):

| phase | µs/call |
|---|---:|
| descriptor rebind | 0.61 |
| command-buffer re-record | 1.24 |
| **submit** | **23.1** |
| **fence wait** | **220.7** |
| memcpy x / y | 4.46 / 2.71 |

Rebind and re-record are negligible. The real cost is exactly what the
roadmap's own evidence line said — genuine submit+fence round-trip
cost — and the only way to remove it is to remove a whole round trip,
which needs the recurrence on the GPU.

**Verdict: blocked as a Sonnet item.** Achievable only as a new GPU kernel
(the recurrence and/or the norm+gate step moved to a compute shader,
enabling a real single fused submit) — Opus tier, and the same class of
premise check that sent the original KDA plan to the Fable gate after G3.
No code changed; nothing shipped.

**Decision: skip, don't escalate to Fable now — this is not a new
question.** `G4-KDA-SPEC-2026-09-04.md` §"Why not the shader, in numbers"
already priced a GPU recurrence kernel at the original Fable gate: floor
~6 ms/token against the CPU plan's ~15, i.e. **~9 ms/token for 2–4 days
and a second numerics path**, and set an explicit trigger, verbatim:
**"Revisit only after items 1–6 of the G3 ranked list are done, if KDA is
then the largest remaining bucket."** G12's fold needs essentially that
same kernel (the recurrence and/or norm+gate on GPU) to let `ko` share a
submit, for a similar-sized payoff (~14 ms/token) — so asking Fable to
re-decide this now would be re-litigating an already-answered question,
not a fresh one, and the trigger condition for reopening it hasn't even
been reached: items 1–6 of the G3 list are G11, G4, G8, G7, G10, G9 — G10
and G11 are still not started. **Skip to G10; the post-G9/G10 re-profile
milestone (already on this roadmap) is the natural point to check whether
KDA has become the largest bucket, which is the one thing that would
justify reopening this with Fable.** G12 stays blocked, not abandoned —
its answer is tied to the same trigger as the original shader question.

## G10: mHC's pre/post, parallelised — the malloc removal did not survive contact

`hyper_connections.h` is shared with DeepSeek V4 (rebuilt clean; not
re-measured — no rig checkpoint, out of this track), so every change here
had to stay safe for a caller this record has never run.

**The parallelisable part.** `coli_hc_pre`'s mix computation is
`mix_count` independent dot products (24 rows at `hc_mult=4`, ~400k MACs
total) against the same input row — parallelised over rows, each row's
own scalar reduction untouched, same reasoning as G7's router fix, not a
SIMD reduction reorder. `coli_hc_pre`'s final collapse (`dimension`
columns, hc-term reduction each) and `coli_hc_post`'s destination×column
mix (`collapse(2)`, hc-term reduction each) parallelise the same way.
Nesting safety already proven by G8's compiled `max_active_levels` probe.

**The malloc removal did not survive contact.** The roadmap also asked to
drop `coli_hc_pre`'s two per-call `malloc`s (mixes, pre — 90 sites/token).
Tried it: since `hc_mult` is bounded to 8 by every loader, replaced both
with fixed-size stack arrays. **Not numerics-neutral on this box.** Once
`hc`'s range is knowable at compile time — whether from the fixed array
size itself or from an explicit `hc <= 8` guard added defensively — GCC
produces different rounding in the small hc-bounded reductions, changing
`last_logits` by ~1.9e-4 absolute (cosine 0.9999999999258, argmax and
`teacher_forcing` both unaffected) with zero change to the source's
logical operation order.

Bisected properly before accepting or rejecting anything: tried
`__attribute__((optimize("no-tree-vectorize")))` (no effect — same exact
delta), `-ffp-contract=off` (changed the delta to a *different* nonzero
value, ruling out a simple on/off toggle), `#pragma GCC unroll 1` on every
hc-bounded loop (no effect), an `asm volatile` aliasing barrier after each
array's declaration (no effect), and `__attribute__((noipa))` (no effect).
None restored bit-identity. Reverting *only* the mallocs — keeping every
`#pragma omp` — gave `max_abs=0.0` directly: the parallelism was never the
problem. **Verdict: keep the mallocs, ship the parallelism.** The malloc
removal was the small piece of this item, not the point of it, and
CLAUDE.md's rule is unconditional here — no numerics change ships
without an env knob and a measured diff in the commit body, and this one
isn't worth either for ~90 tiny allocations/token.

**Oracle**, vs `da99b9c` (G9), 3 GPUs, same histogram, teacher_forcing and
last_logits by `diff`, no tolerance: short prompt **bit-identical**
(`max_abs=0.0`); ~700-token prompt (1260 prefill positions) **bit-identical**

Identical routing in both (`experts=34099`, `cpu n=8909`, `mmap serve=3358`,
`binds gpu=1056 cpu=2302`) — the same work, the same code path, 1.86× apart
on one bucket. The error localises exactly where the mechanism predicts:
**the CPU expert path is the only thing that streams ~985 MB/token out of
mmap'd model pages**, so an incompletely warm page cache taxes it and
nothing else. RP1 checked `fincore` on the *tail* shards only and read
"resident"; the full set was **93.2%** resident, and the missing 7% is
~69 MB of faults per token landing entirely on this bucket. CLAUDE.md says
it in one line — *"A cold run pays 100k+ major faults and is not a
baseline"* — and RP1 half-checked it. Corrected procedure: `fincore` across
**all 62 shards** and assert 100%, not a spot check.

Two other confounds found and removed at the same time, neither of which
turned out to matter much on its own: the box was running **netdata**
(8% of a core, and driving `dockerd` to poll constantly) — stopped for these
runs; and `ps`'s `%CPU` for `dockerd` reads 22% but that is a **4-day
lifetime average**, instantaneously it is 0.0%. The box now measures 98–99%
idle. Clocks hold 3.45–3.63 GHz throughout, so frequency is not a variable.

## G11 (part 1): the expert path fused — small, bit-identical, and the item re-sized

RP1 said the expert path was worth chasing because only 57% of the
core-time in the CPU-expert window was in the kernel. Two microbenchmarks
were built to size that before touching the engine (`g11_bench.c`,
`g11_path.c`; both cycle over ~400 MB of experts so the 128 MB L3 cannot
hide the streaming, and both check every variant against the in-tree kernel
for bit-exactness before timing it).

**What the microbenchmarks said.** On the isolated kernel at 8 threads:
the in-tree kernel does 21.95 GB/s; a bit-trick nibble→float decode (which
is *exactly* bit-identical — it builds the same float by OR-ing into a
mantissa instead of `cvtepi32_ps`) gives 1.03×; adding a second independent
accumulator to break the FMA dependency chain gives **1.30×** but is not
bit-identical; four accumulators is worse than two. On the full expert
path, fusing the three `parallel for` regions into **one region with three
worksharing constructs** (gate+up share one, then the swiglu, then down) is
**bit-exact and 1.07×**; adding the faster kernel on top only reaches 1.13×.
**Once the path is fused, the faster kernel is nearly worthless** — which is
why nothing numerics-changing is shipped here.

**What the engine said.** `mlp3_cpu` now issues one parallel region instead
of three, and the swiglu is shared across the team instead of running
single-threaded between them. `GLM53_EXPERT_SPLIT=1` restores the old path
for A/B (it is not a numerics knob — both paths are bit-identical).
Four paired runs, alternating, 100% resident, quiet box:

| | split (old) | fused | Δ |
|---|---:|---:|---:|
| `[PROF] cpu` | 5.153 s | 4.945 s | **−1.62 ms/token (−4.0%)** |
| `[OPTIME] ffn_moe` | 8.938 s | 8.650 s | **−2.25 ms/token (−3.2%)** |
| `[PROF] eg` | 6.225 s | 6.021 s | −1.59 ms/token (−3.3%) |

Reproducible to 0.3% on the internal timers. **Fresh-process tok/s cannot
resolve it** — the four runs scatter 5.70–6.27 tok/s (±10%) on GPU-submit
jitter while the CPU-side timers hold to 0.3%, so for a CPU-path change the
timers are the sensitive instrument and the wall-clock is not. Stated
plainly: this is **~1% of the decode token**, not the "−25 to −45" the
roadmap carried.

**Oracle**, vs HEAD, 3 GPUs, same frozen histogram, teacher_forcing and
last_logits by `diff`, no tolerance: short prompt **bit-identical**
(`max_abs=0`), and the old path under `GLM53_EXPERT_SPLIT=1` is also
bit-identical, as it must be.

**Serving gate**, `rome_bench.sh`, against G10's 2.60/2.75:

| run | rotating median |
|---|---:|
| g11-run1 | 2.67 tok/s |
| g11-run2 | 2.71 tok/s |

**The gate cannot resolve this change and it is not claimed to.** G10's own
two runs spread 2.60–2.75; these two land inside that spread. A ~1% effect
is below this harness's resolution — which is the honest reading, not a
disappointment: the measured delta is the paired fresh-process one above
(−4.0% on `[PROF] cpu`, reproducible to 0.3% across four alternating runs),
and the gate's job here is to show **no regression**, which it does.

**Verdict.** Shipped, because it is free, bit-identical, and removes ~140
OpenMP regions per token in the direction RP1's spin analysis pointed. But
G11 as "the big kernel item" is over: its bucket is 40.3 ms/token, the path
half of it is worth ~2, and the kernel half is worth ~1.06× once the path is
fused and is not bit-identical. **The remaining money is in KDA's 35 ms/token
of GPU submits, not here.**

## Fable gate 2: the KDA recurrence goes to the GPU — reversed on the first gate's own terms

`G4-KDA-SPEC-2026-09-04.md` rejected a GPU recurrence shader and set the
condition for revisiting it: *after items 1–6 of the G3 list are done, if
KDA is then the largest remaining bucket*. §RP1-CORRECTION made both halves
true for the first time — G11 closed today, and KDA is the largest bucket
at 53.3 ms/token. The decision is **yes**, written up as
`G12-KDA-GPU-SPEC-2026-09-05.md`, and G12 is reopened as the item that
executes it.

**What changed the answer.** Not the ms alone. (1) `coli_vk_attn_qprep`
already records *batched matmuls → norm stage → matmul* into one command
buffer with compute barriers and has a CPU-reference self-test — so "from
scratch" now means one shader, the recurrence, not a chain. (2) The expert
tier already *is* a GPU/CPU numerics fork by residency, and the engine
tolerates it; what is new is that KDA state is recurrent, which the oracle
addresses with a 1000-step shader-only drift test and a long-horizon greedy
identity test rather than a tolerance. (3) `coli_kda_step` is 64
independent 128×128 tiles plus an elementwise conv: one workgroup per head.

**What the first gate got right and this one keeps.** No credit for idle
CPU cores (sequential dependency, nothing to overlap). Off by default
behind `COLI_KDA_GPU`. And the sizing is done from what is actually
removed, not from the bucket: one round trip (34 × 0.244 = 8.3 ms) plus
the CPU recurrence (18.6 ms) minus three latency-bound dispatches (5–10 ms)
= **−15 to −22 ms/token, 9–14 %** — the roadmap's "up to −35" counted
`proj`+`ko`'s matvec compute, which stays on the GPU either way, and is
corrected.

**One constraint the first spec never faced.** `kda_state`/`kda_window`
are exported as raw spans for segment migration (`glm53.c:3768–3771`).
GPU-resident state must not be read back per call — 136 MB/token over PCIe
is ~5 ms, a third of the win — so the CPU copies go stale while the knob is
on and are re-synced only at export and import. The spec names both sync
points and makes the migrate-then-continue test part of the oracle.

**Numeric stop conditions:** shader-only relative error ≤ 1e-5 over 1000
steps, no NaN/Inf; integrated greedy text identical on every `rome_bench`
prompt through 128 tokens and across the 1260-position long prompt,
last-logit cosine ≥ 0.99999 at 8/64/128; `[OPTIME] kda` **< 1.0 ms/call**
is go, > 1.2 is stop-and-ship-off. Opus executes; Fable is asked again
only if Stage 2 diverges, and the answer to loosening the oracle should be
no.
