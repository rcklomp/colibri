# M1 + M5 microbenchmarks: brief (2026-09-22, design rev 4 §4)

Two measurements from the Franken-engine design, written as one harness
because they share the shapes and the build. Nothing here touches the
gateway; the harness runs under the rig lock while GLM idles, and only the
orchestrating session runs it.

## Why these two first (from §F11-M0, corrected)

Qwen3.8-Flash-Next at its shipped quant is FULLY resident on three cards and
llama.cpp still needs 34–40 ms a token. The bytes a token reads from VRAM are
~6.2 GB (48 layers x ~104 MB of Q8_0 trunk, plus 480 expert evaluations x
~2.4 MB); at 800 GB/s that is ~7.5 ms if the three cards run in sequence. The
4–5x gap is launches, syncs and kernel efficiency, not streaming. M5 measures
the launch/sync floor on this hardware; M1 measures what each engine's expert
kernel achieves against the bandwidth bound on the real shapes.

## M1: routed-expert kernel head to head

For each candidate, one process, weights for all 512 experts of ONE layer in
VRAM on one card (~1.2 GB), an `ids[10]` array on the device, and the full
MoE step for one token: gate+up on 10 experts, SiLU*up, down on 10 experts,
weighted sum. Batch 1 (decode) and batch 32 rows (prefill/concurrent slots).
Warm-up 100, then 1 000 iterations, on-device timing (hipEvent pairs around
the whole step), report median and p10/p90 in µs, and achieved GB/s =
bytes of expert weights touched / median. The bandwidth reference is a plain
read kernel over the same buffer on the same card (report its GB/s next to
each candidate).

Candidates:
1. **llama.cpp** `mul_mat_vec_q_moe` via the public ggml API (`ggml_mul_mat_id`
   with the HIP backend from `~/src/llama-glm53/build-hip`, one graph with the
   gate/up fusion the server uses), IQ3_S gate/up + IQ4_NL down exactly as the
   file has them. This is the served path; it anchors the comparison.
2. **hipFire** `gemv_mq4g256v2_moe_gate_up_k8_indexed` and
   `..._moe_down_k8_indexed_batched_expanded` (`~/src/hipfire/kernels/src/`),
   MQ4G256V2 format. Two known misfits to report, not work around silently:
   K_TOP is 8 in the kernel (run at 8, say so); down has K=640, not a multiple
   of the 256-group (run down at K=768 zero-padded and report the padded bytes).
3. **Colibri** `c/shaders/qmatmul_gate_up.comp` / `qmatmul_tile.comp`
   (int4-g64, Vulkan) through `c/backend_vulkan.c` as the engine calls it:
   the number to report is the same on-device time AND the host-visible time
   per call, because the 0.3 ms blocking call (§F3-STEP2A) is part of what
   this path costs today.

Numerics for every candidate: the same fp32 activations, weights quantised
from one fp32 source with each format's own quantiser; output compared to an
fp32 CPU reference on the DEQUANTISED weights (max abs, cosine) so a wrong
layout shows as O(1), not as a speed number.

## M5: the launch and sync floor on gfx1100 (HIP, ROCm 7.14)

Same binary family, one card unless stated, 10 000 iterations, medians:
1. `hipLaunchKernel` of an empty kernel back to back on one stream: µs per
   launch (this is the cost of every node in a llama.cpp graph).
2. The same 2 000 launches captured into one `hipGraph`, `hipGraphLaunch`
   once: µs per node.
3. `hipEventRecord` + `hipStreamWaitEvent` between two streams on one card.
4. One hidden vector (2 560 f32, 10 KB) card->card: `hipMemcpyPeerAsync`
   with P2P enabled, and through pinned host memory; latency for each pair of
   cards, the shared-link pair labelled (amd-smi PCI order: GPU 1 = 83:00.0
   and GPU 2 = 86:00.0 share the upstream link).
5. A synthetic 48-layer token: per layer one Q8_0 GEMV 10240 x 2560 (any
   correct int8 kernel; hipFire has one) plus the M1 MoE step, first as
   separate launches, then as one hipGraph: ms per token on one card. This is
   the number the design's §1(b) rests on.

## Build and run discipline

- Sources under `tools/hot-expert/m1/` in a worktree `~/src/colibri-m1`
  (`git worktree add --detach ~/src/colibri-m1 hot-expert-tier`), removed
  when the item lands. Build in the docker image
  `rocm/dev-ubuntu-24.04:7.14.0-full` (hipcc; llama.cpp's HIP build is in
  `~/src/llama-glm53/build-hip`, link its `libggml*`).
- The agent BUILDS and writes the run script; it does not run anything on the
  GPUs. The orchestrator runs it under `rig_lock.sh` with GLM idle, after the
  M0d chain has finished, and records §M1 / §M5 in the record.
- Output is one line per measurement in `key=value` form so the record row is
  a copy, and a JSON file next to it.
