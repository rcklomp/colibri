# Qwen3.8 / GLM-5.3 on an EPYC 7F32 + 3× RX 7900 XTX box — placement measurements (2026-09-04)

Lab record, same spirit as the rest of this directory: what was measured, how,
and what it decided. Harness sources are next to this file
(`rome_cpubench.c`, `rome_vkbench.c`, `rome_fp8test.c`, one-file harnesses,
build lines in their headers); they hardcode
Qwen3.8 shapes and build against `quant.h` / `backend_vulkan.o`.

## The machine

| | |
|---|---|
| CPU | AMD EPYC 7F32, 8 cores / 16 threads, Zen 2 (AVX2+FMA+F16C, **no AVX-512**), 128 MB L3. SMT siblings are `i` and `i+8`. |
| RAM | 8 × 32 GB DDR4-2400. Measured read bandwidth 18.8 / 35.7 / 57.1 / 70.9 / 91.6 GB/s at 1 / 2 / 4 / 8 / 16 threads. |
| GPUs | 3 × Radeon RX 7900 XTX (gfx1100, RDNA3), 24 GB each, RADV (Mesa 26.0.8, Vulkan 1.4). Cooperative matrix and int8 dot product are exposed; **no FP8 in hardware**, `fmt=8` is emulated in the shader. |
| Disk | one NVMe. Both checkpoints (Qwen 173 GiB FP8, GLM 182 GiB int4) fit in the 247 GB page cache one at a time, not together. |

The one fact that reshapes every prior number in this repository: on this box
**the disk is not the wall** once a checkpoint is in the page cache. Every
"expert streaming is disk-bound" assumption in `docs/` is about 25–128 GB
machines.

## Baselines (before any change on this branch)

Prompt: 48 tokens, greedy, 64 new tokens, expert cap 512, page cache warm
(`fincore` checked), `COLI_TIMERS=1`.

|---|---:|---:|---|
| Qwen3.8 CPU 16 thr, cap 64 | 1.16 tok/s | 18.3 s | routed 555 ms, resident BF16 158, deltanet 120, lm-head 13 |
| Qwen3.8 CPU 16 thr, cap 512 | 1.40–1.51 tok/s | 13.4–17.5 s | routed 383–395, resident 156–162, deltanet 120 |
| Qwen3.8 `qwen38-vk`, 3 GPUs, lazy tier | 1.57 tok/s (128 tok) | 18.8 s | routed 125, resident 196 (!), untimed uploads |
| GLM-5.3 `glm53` Vulkan, 3 GPUs (1296+1695+1695 preloaded from `.glm53_explain.bin`), **8 threads** | **3.17 tok/s** | 60 tok | reproduces the 3.16–3.26 tok/s recorded in the Sep 2 commits (f4fbc4c…573871f) |
| same, 16 threads bound | 2.78 tok/s | | the launcher pins engines to physical cores; 16 threads fight the RADV threads |
| same, 16 threads unbound | 2.02 tok/s | | |
| GLM-5.3 `glm53` CPU-only, 8 threads | 1.97 tok/s | | matches the 1.97–1.98 in the Sep 3 commits |

(For scale: the owner's llama.cpp HIP build of the same GLM checkpoint does
3.15 tok/s on this box with 18 layers offloaded.)

A first GLM measurement in this session read 1.41 tok/s and was wrong three
ways at once: 16 unbound threads, a page cache just evicted by warming Qwen
(167k major faults), and the 6,218-entry `.glm53_usage.bin` histogram that
left the third GPU empty. A bisect of the Sep 3 Vulkan commits at equal
conditions (573871f 2.02, 6da3910 2.07, both 16 threads) showed **no code
regression**: the shader's fmt=8 branch and the dev2/dev3 upload changes cost
GLM nothing measurable. Two operational lessons: GLM's dev2/dev3 preload
loops stop on a count cap only (`COLI_VK_EXPERTS2/3`), so an unlimited cap
spills the tier into host memory (6,458 "resident" experts = 91 GB, evicting
the page cache); and never run a foreign-branch `glm53` on this box
(`eabeb9a`'s cache sizing takes MemAvailable and OOM-thrashed the machine
for 25 minutes).

**Qwen** is where the GPU tier underdelivered: as found it was +8% over the
CPU fresh-process (1.57 vs 1.45) and +27% in steady state per the Sep 3
commits (5.0 vs 3.9, run 2 of 3 through the persistent server at 8 threads),
against a 3× per-expert advantage in the microbenchmarks. The reason is not
the GPU: see the per-op numbers.

## Where the Qwen CPU token went (perf, flat, 16 threads)

```
22.9% + 20.0%  libgomp barrier spin      <- 15 threads waiting for 1
22.5%          matmul_fp8 (routed experts)
18.1%          q38_matmul_bf16 (dense)
 3.6%          kernel spinlock (page-table lock under concurrent faults)
```

The waiting was page faults: an expert served from the file mapping is bound
by pointer (no copy) and first touched inside the 16-thread matmul; the thread
that faults (minor with a page-table lock, or major to NVMe after eviction)
stalls the other fifteen at the region barrier. Isolated, the same FP8 kernel
ran 4–6× faster than inside the engine (0.20 vs 0.8–1.1 ms per expert).

## Per-op placement matrix (Qwen3.8 shapes, this box)

CPU: real engine kernels, weights rotated through pools larger than L3.
GPU: real `backend_vulkan.o` through its public API, distinct-expert pools
larger than Infinity Cache, times include submit+fence round trip.

| op | shape | CPU (best) | GPU dev0 Vulkan | verdict |
|---|---|---:|---:|---|
| submit + fence round trip | tiny matmul | — | **53–66 µs** | the engine's comment says 0.4 ms; here it is 7× cheaper, so per-layer submits are affordable |
| BF16 dense GEMV | 2560→10240 | 0.52–0.57 ms, 92–101 GB/s (DRAM-bound) | no BF16 shader; int8 proxy 0.198 ms (132 GB/s eff.), fp8-emul 0.342 ms | CPU is at its bandwidth floor. GPU int8 is 2.9× faster per call but needs a numerics change or a new BF16 `fmt`; per token this is 8.5 GB → ~85 ms CPU floor vs ~50 ms GPU incl. ~48×5 submits |
| BF16 dense GEMV | 6144→2560 | 0.32 ms, 99 GB/s | int8 0.171 ms, int4 0.147, fp8 0.295 | as above |
| LM head | 2560→248320 | 12.3 ms, 104 GB/s | int8 1.58 ms (403 GB/s), int4 1.36 ms | GPU wins 8× **if** the head is int8/int4; kept on CPU for numerics |
| BF16 dense, prefill S=32 | 2560→10240 | engine kernel 9.0 ms (187 GFLOP/s); 4-accumulator variant 5.1 ms (330 GFLOP/s) | — | a 1.8× CPU prefill kernel win is available (not landed: prefill is dominated by expert reads) |
| int8 dense GEMV (AVX2 `maddubs`) | 2560→10240 | 0.27 ms, 99 GB/s | — | int8 dense on the CPU would halve the dense floor; changes numerics, not done |
| routed experts, decode (10 experts) | 2560→640 ×2, 640→2560, FP8 | engine kernel 2.0 ms/layer = **96 ms/token** (24.6 GB/s, ALU-bound); F16C decode **70 ms/token** (33.9 GB/s) | fp8-emul group 0.467 ms/layer = **22 ms/token**; int8 13.5 ms; int4 12.6 ms | GPU wins 3× per expert **when resident**; VRAM holds ~14k of 24.6k experts |
| routed experts, prefill rows=8 | same | — | fp8 1.66 ms/layer (0.166 ms/expert), int8 1.11 | FP8 emulation costs 1.5× vs int8 on the GPU: real, but not decisive |
| 3 GPUs, one expert group each | K=10 per device | — | sequential (engine as found) **2.37 ms/layer = 114 ms/token**; concurrent issue/take **0.63 ms = 30 ms/token** | the found engine serialised the three GPUs |
| 4 dense tensors, one submit vs four | I=2560 | — | 0.247 vs 0.378 ms | batching dense dispatches pays even at 55 µs/submit |

**The precision↔WMMA hypothesis** from the handoff: partly right, mostly
moot for decode. FP8 emulation makes the GPU expert GEMV 1.7× slower than
int8 at the same bytes (0.467 vs 0.282 ms per 10-expert group), but decode is
a GEMV, so cooperative-matrix hardware never enters; the emulated FP8 path is
still 3× faster per expert than the CPU. Converting Qwen experts to int8/int4
would buy ~9 ms/token on the GPU and halve the VRAM per expert (twice the
resident tier), at the cost of a second copy of the checkpoint and a
numerics change. Worth doing for VRAM, not for WMMA.

**Why the Qwen tier gained so little** (measured, not inferred): (1) the
CPU expert path was 4–6× slower than its own kernel because of page-fault
stalls, and the GPU path still ran that CPU path for every non-resident
expert; (2) the three GPUs were driven sequentially (114 ms/token at full
residency); (3) the tier filled lazily, so 4.7 MB uploads landed inside
decode, and the driver's spin-wait threads took cores away from the dense
matmuls (resident BF16 149 → 196 ms). None of that is RDNA3's fault.

## Changes landed (branch `perf/rome-cpu-path`), each A/B'd on this box

Same prompt, same 64 greedy tokens in every run (text identity), last-token
logits compared against the pristine binary where noted.

| change | Qwen CPU 16 thr | notes |
|---|---:|---|
| pristine | 1.45 tok/s (1.40 / 1.51) | |
| `MADV_POPULATE_READ` at expert bind (`Q38_MMAP_POPULATE`) | ≈ +10% | routed 395 → 299 ms with the other two changes off |
| F16C E4M3 decode in `matmul_fp8` | 0.203 → 0.145 ms/expert isolated | exhaustive 256-code check and matmul outputs bit-identical to the LUT path |
| DeltaNet / attention projections in one OpenMP region (`Q38_DENSE_MULTI`) | ≈ +2% | resident 132 → 125 ms; bit-identical rows |
| all three | **1.90–1.93 tok/s** (+32%) | routed 231 ms, resident 125–129 ms |
| + 8 threads, one per core (`OMP_NUM_THREADS=8 OMP_PLACES=cores`) | **2.35 tok/s** (+62%) | routed 142 ms; dense loses 19 ms; FP8 kernel is ALU-bound, SMT halves it |
| `OMP_WAIT_POLICY=passive` | 1.57 tok/s | worse: ~2,000 regions/token, wake-ups cost more than spinning |

| change | Qwen `qwen38-vk`, 3 GPUs | notes |
|---|---:|---|
| as found (lazy fill, sequential devices) | 1.57 tok/s | |
| + CPU changes, still lazy fill (`Q38_VK_PRELOAD=0`) | 1.40 tok/s | lazy uploads dominate |
| + heat-ranked preload + concurrent issue/take + CPU share overlapped | **2.77 tok/s** (64 tok), **2.99 tok/s** (128 tok) | 9,396 experts (every one with history) preloaded in 24 s, 24.4 GB on dev0; TTFT 8.8 s; routed 69–104 ms |

Two follow-ups measured and **rejected** (code removed, not shipped as knobs):

| tried | Qwen CPU | why it lost |
|---|---:|---|
| `num_threads(8)` on the FP8 kernel inside the 16-thread pool (threads 0–7 = 8 distinct cores, siblings are `i`/`i+8`) | 1.70 tok/s vs 1.90 | the eight idle pool threads spin on the sibling hyperthreads and slow the eight that work (resident BF16 125 → 166 ms too). Only a genuinely 8-thread pool helps. |
| two FMA chains per 128-block | 1.68 / 1.90 at 8 / 16 threads: no change | the kernel is not FMA-latency-bound; logits differed from the single chain by 8e-6 (argmax same) for nothing |

Numerical identity, last-token logits after the same 64 greedy tokens,
against the pristine binary: prefault + F16C + fused dense **max abs diff 0**
(bit-identical); `qwen38-vk` 3-GPU path max abs diff 7.6e-6, cosine 1.0,
same argmax (the GPU FP8 dot products accumulate in a different order).

Routing history matters for the tier: after the benchmark runs grew
`.coli_usage` from 9,396 to 11,244 nonzero experts, the same 3-GPU 128-token
run went from 2.99 to **3.38–3.39 tok/s** (TTFT 8.5 s).

Final numbers with the committed tree (same prompt, cap 512):

| configuration | decode | routed | resident BF16 | expert-read |
|---|---:|---:|---:|---:|
| `qwen38`, 16 threads | 2.00 tok/s (64 tok) | 221 ms | 127 ms | 41 ms |
| `qwen38`, `OMP_NUM_THREADS=8 OMP_PLACES=cores OMP_PROC_BIND=close` | 2.28 tok/s (64 tok) | 143 ms | 145 ms | 57 ms |
| `qwen38-vk`, 3 GPUs, 16 threads | 3.38 tok/s (128 tok) | 70 ms | 133 ms | 64 ms |
| `qwen38-vk`, 3 GPUs, **8 threads one per core** | **4.05 tok/s** (128 tok) | 60 ms | 114 ms | 27 ms |

The last row is the recommended launch on this box: 2.8× the pristine CPU
engine, 2.6× the pristine `qwen38-vk`. With the GPUs doing the experts, the
CPU's job is the dense BF16 stream, and eight threads leave the RADV
submit/fence threads their own hyperthreads instead of fighting sixteen
spinners for them (resident 133 → 114 ms). Both `qwen38` rows are
bit-identical to the pristine binary on last-token logits; the 3-GPU path
was checked at 64 tokens (max abs 7.6e-6, same argmax) — a 128-token dump is
a different position and is not comparable, which is why no 128-token
identity figure is quoted.

## Steady state: the regime the server runs in (`tools/datapoint.py`, 8 threads)

Persistent `SERVE=1` engine, page cache evicted before load, 80 completion
tokens, expert cap 512; one cold request, the same prompt twice (upper
bound), then two different prompts (the tool's primary serving result).
`datapoint.py` sets `OMP_NUM_THREADS` to physical cores, as the `coli`
launcher does, so these are 8-thread numbers, and the pristine rows match the
3.9 / 5.0 tok/s in the Sep 3 commit messages.

| engine | warm-identical (upper bound) | rotating prompts, median | cold first request | cold TTFT |
|---|---:|---:|---:|---:|
| pristine `qwen38` (CPU) | 4.11 tok/s | 2.87 | 2.54 | 19.5 s |
| patched `qwen38` (CPU) | **4.70** (+14%) | 2.89 (±0) | 2.47 | 11.9 s |
| pristine `qwen38-vk`, 3 GPUs | 5.34 | 2.72 | 2.08 | 18.3 s |
| patched `qwen38-vk`, 3 GPUs | 5.35 (±0) | **3.69** (+36%) | **3.59** (+73%) | 7.1 s |

Read against the fresh-process numbers above: the pristine engine was never
1.45 tok/s in service, only in a fresh process that pays every first-touch
fault. In steady state the branch buys +14% on the CPU path, nothing on the
GPU upper bound (the lazy tier had already filled and hits 100% on a repeated
prompt), +36% on changing prompts, and a much better first request (the
preload of 14,673 experts costs 90 s at load, then pays back on every cold
request: 7 s TTFT instead of 18). The rotating-prompt CPU number did not move:
prefaulting relocates the first-touch cost of new experts, it does not remove
it, which is the case for populating the whole mapping at load (backlog 3).

## What the data killed

- **"VRAM-reside Qwen's dense/attention/shared-expert weights" as the first
  move** (the prior audit's #1). It is real (~85 ms/token CPU floor vs ~50 ms
  on the GPU) but third in line behind the two 100+ ms items above, needs a
  BF16 shader format or an int8 conversion, and competes with experts for the
  same 72 GB. Now evidence-ranked, not killed.
- **"GPU loses to CPU because RDNA3 lacks FP8"**: emulation costs 1.7× on the
  GPU, the GPU still wins 3× per resident expert.
- **AVX-512 / VNNI ideas**: not on this silicon.
- **Bigger expert cap as a footgun fix** (`cap=1` default): on this box the
  mmap path makes a miss a pointer bind, so cap only changes hit telemetry and
  the batch loader's willingness to prefault; 512 is right here.

## Backlog, ranked by measured delta per token (Qwen, from the 2.99 tok/s state ≈ 334 ms)

1. **Dense set off DRAM** (resident BF16 137 ms + shared 19 ms): int8 on the
   GPU measured 132–400 GB/s effective vs 100 GB/s CPU; ~5 submits/layer ×
   48 × 55 µs = 13 ms. Expect −80 to −100 ms. Needs a BF16 `fmt` in
   `qmatmul.comp` (numerics-preserving) or an int8 dense conversion, and the
   DeltaNet/QSA cores stay on the CPU with per-layer round trips.
2. **Expert-read 71 ms (`MADV_POPULATE_READ` cost of first-touch CPU misses)**:
   goes to zero in steady state; for cold sessions, populate at load (whole
   mapping, 173 GiB fits) behind a knob.
3. **MTP speculative decoding** (tech report, Table 4: mean accepted length
   4.06 with four-step MTP reusing QSA indices). On a bandwidth-bound decode
   the dense 8.5 GB is read once per verify step, experts ~4×: ≈ 2.4× tokens
   per second at equal bytes. Largest multiplier available; largest effort
   (MTP module weights, index reuse, verify path).
4. **More routing history for the preload**: only 9,396 experts had nonzero
   counts; VRAM has room for ~14,000. Longer/rotating usage capture fills it.
5. **CPU prefill kernel** (4-accumulator BF16, 1.8× on S=32) and GPU prefill
   for resident experts: TTFT, not decode.
6. **GLM-5.3**: 3.17 tok/s on the tier at 8 threads equals llama.cpp HIP's
   3.15. CPU-side items are the scalar KDA inner loop and the O(context²)
   pooled-key recompute in `sparse_index.h`; the mmap expert path likely
   carries the same first-touch fault stall as Qwen's did (not measured).

## C0: `tools/rome_bench.sh` harness, gate result

One script (drop caches, warm one model, verify residency with `fincore`,
pin `OMP_NUM_THREADS=8 OMP_PLACES=cores OMP_PROC_BIND=close`, set the GLM
caps, run `datapoint.py --mode persistent`, extract the rotating median from
its Workload summary table). Gate: two consecutive runs of the same config
within 3%.

`qwen38-vk`, **3 GPUs, tier verified up** (14,673 of 21,858 hot experts
preloaded in 99–100 s, dev0 24.4/25.7 GB, asserted by the harness), cap=512,
80 completion tokens, same prompt suite:

| run | rotating median | warm-identical | cold | cold TTFT |
|---|---:|---:|---:|---:|
| gpu-real1 | 4.12 tok/s | 5.43 tok/s | 3.47 tok/s | 7.65 s |
| gpu-real2 | 4.13 tok/s | 5.44 tok/s | 3.47 tok/s | 7.48 s |

Delta on the headline (rotating median): |4.13 − 4.12| / 4.12 = **0.24%**,
against a 3% gate. **Pass.**

These sit where the steady-state table's patched 3-GPU row leads one to
expect — warm-identical 5.43 vs 5.35, cold 3.47 vs 3.59, cold TTFT 7.6 vs
7.1 — which is the corroboration that the tier really is up. The rotating
median is higher than that row's 3.69, consistent with the routing histogram
having grown since (21,858 hot experts now, against the 9,396→11,244 the
section above describes); that is the Q0 effect, measured here incidentally,
not a change in the engine. Note the same accumulation makes consecutive
runs not perfectly independent: `.coli_usage` is written back, so run N+1
preloads from a slightly richer history than run N.

> in use**. The evidence is in the runs themselves: `datapoint.py` emitted no
> `| GPU |` row and no `| expert tiers |` row (it prints both whenever the

> numbers belong against the patched-`qwen38` CPU line (2.89 rotating), not
> against a GPU row, and they are superseded by the verified table above.
> The harness now asserts the engine's own preload line and **refuses to
> record** a Vulkan config that comes up with an empty tier.

On cache state: the harness's own `echo 3 | sudo tee /proc/sys/vm/drop_caches`
needs interactive sudo on this box, so it warns and continues. That turns out
not to matter for the model shards, because `datapoint.py` evicts them itself
with `posix_fadvise(DONTNEED)`, which needs no privilege — and it labels the
row "cold request (cache evicted before engine load)" *only* when that
eviction succeeded, which is what these runs printed. So the `cold` column
above is a genuine cache-evicted cold start, and it lands where the
steady-state table's evicted cold rows do (3.47 vs 3.59). The sudo drop is
the broader whole-system eviction; the per-shard one is what the cold number
actually rests on. (An earlier revision of this section claimed the opposite —
that these were warm-cache runs — which was wrong.)

Two extraction bugs were found and fixed while building this harness, both
against the same class of mistake (a fixed `awk` field index into a table
whose column count differs by row): the rotating figure first read the
Decode table's "rotating 1" row instead of the Workload summary's median
(2.87/2.86 tok/s instead of the correct 3.29/3.27), and the cold figure read
the TTFT column instead of decode tok/s (13.00 instead of 2.29). Both are
fixed in the committed script; the gate1/gate2 numbers above are post-fix.
