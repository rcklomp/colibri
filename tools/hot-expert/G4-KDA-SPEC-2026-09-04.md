# G4 spec: the KDA path (decided from G3, 2026-09-04)

The roadmap's gate after G3 asks for one page: which KDA approach, and the
numerics oracle by name. Evidence is the G3 section of
`ROME-3x7900XTX-2026-09-04.md`; nothing below is inferred from anything else.

## Decision

**CPU. Parallelize the recurrence across its 64 independent heads, stop
recomputing a constant, stop shifting the conv window. No GPU shader.**

The three roadmap options were built on a description of KDA that the
profile does not support: its inner loops are already AVX2-vectorized (GCC
`-fopt-info-vec`), the "scalar loop over L=512" belongs to MLA, and at
2.30 ms/call against a 0.9 ms single-core DRAM floor (16 MB of state traffic
at 18.8 GB/s) it is not bandwidth-bound — it is single-threaded, on one of
eight cores, with ~57k libm transcendentals and 24,576 twelve-byte
`memmove`s per call. Those three things are what the fix removes.

## What changes

1. **Head parallelism in `coli_kda_step`** (`c/delta_attention.h` — a
   *shared* header: `glm53`, `kimi_k3`, `qwen36` all include it).
   `#pragma omp parallel for` over `head`; each thread needs its own
   `memory[v_dim]` scratch, so `coli_kda_scratch_floats()` grows by
   `omp_get_max_threads() * v_dim` and the callers' allocations follow it
   automatically. Guard with `#ifdef _OPENMP`. Nothing about one head's
   arithmetic, or its order, changes.
2. **`expf(alog[h])` once, not 8,192 times** (`kda_layer`, `c/glm53.c`).
   `alog` is a weight; precompute `exp(alog[h])` per layer at load (64
   floats) and read it in the decay loop. Same `expf` of the same input:
   the same bits.
3. **Ring index for the conv window** (`coli_kda_step` + its callers). The
   window is `[channel][kernel]` and every token `memmove`s each channel's
   history left by one — 835k calls per token across 34 layers, 2% of all
   cycles. Keep a per-layer position and index `history[(pos + tap) %
   kernel]` instead, applying the taps in the same oldest-first order so the
   summation order, and therefore the result, is unchanged. The position is
   new per-layer state next to `kda_window` (one `int`, zeroed where the
   window is).

That is phase 1, and it is the whole of G4. Expected: 2.30 → ~0.4–0.5
ms/call, **78 → ~15 ms/token**.

Phase 2, *only* if phase 1 lands and the remaining ~41k transcendentals per
call (decay sigmoid, SiLU on the conv output, `expf(decay[k])`) still show
in `[OPTIME]`: a vectorized AVX2 `exp` approximation. That **changes
numerics** and ships behind an env knob, off by default, per CLAUDE.md.

## What does not change

The recurrence's arithmetic and its order within a head; `-ffast-math` is
not an option; no data leaves the CPU. `COLI_KDA_CPU` and the Vulkan
projection batching around the step are untouched.

## Oracle, by name

Phase 1 is **bit-identical**: `teacher_forcing` line identical *and* the
`--logits` `last_logits` line identical, checked with `diff` (not a
tolerance) against the pristine binary, 3 GPUs, the same histogram copy —
on the standard prompt *and* on the 690-token document from the record, so
the ring index is exercised across many wrap-arounds of `kernel = 4` and the
state across a long prefix. The caveat in `README.md` applies: the resident
set must be the same in both runs, which the histogram copy guarantees.

Because the header is shared: `kimi_k3` and `qwen36` must **rebuild clean**,
and each must pass its own oracle wherever a checkpoint exists on the rig
(their tiny fixtures need torch, which the rig does not have — see the C1
finding; a real-checkpoint `teacher_forcing`/logits diff is the substitute,
as it was for G1/G2). A shared-file change that is only verified on `glm53`
does not merge.

Phase 2's oracle is the record's: cosine, max-abs and argmax of the last
logits against pristine, shipped only within the documented near-tie
tolerance, knob off by default.

## Gate

`[OPTIME] kda` ms/call before and after in the same fresh-process run
shape (128 greedy tokens, `COLI_TIMERS=1`): **2.30 → ≤ 0.6**. Then the
serving number: `rome_bench.sh glm53` rotating median against G2's
1.69–1.71 tok/s, two runs, both reported. The `[OPTIME]` split is the
diagnosis; the rotating median is the result.

## Effort and tier

About one day. Opus: it edits a shared numerics kernel and its scratch
contract, and the parallel version has one non-obvious requirement (the
per-thread scratch) that a copy-and-measure port would get wrong silently
(a shared `memory[]` across heads would corrupt every head's read-back and
still produce plausible tokens — exactly the failure mode the `README.md`
warns the `teacher_forcing` line exists to catch).

## Why not the shader, in numbers

A GPU recurrence kernel does not exist in `backend_vulkan.c`; it would be
from scratch. Its floor here: 16 MB of state over VRAM bandwidth ≈ 0.02 ms,
plus two ~55 µs submits, with 136 MB of state resident in VRAM ≈
0.15–0.2 ms/call → ~6 ms/token. Against the CPU plan's ~15 ms that is
~9 ms/token, 2.4% of the token, for 2–4 days and a second numerics path.
Revisit only after items 1–6 of the G3 ranked list are done, if KDA is
then the largest remaining bucket.
