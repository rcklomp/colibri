## 2. What the session found, in the order a reader should care

1. **GLM prefill is DMA-rate-bound, and the cause is not where it looked.** Device timeline
   (`--timeline`): card 0's embedding upload waited ~3.0 s of every ~4.4 s chunk behind the staging
   ring's DMAs; the host is not late. Moving the upload to a kernel (default now, `--embed-upload-dma 1`
   restores the old path) is bit-exact and worth -3.3 %; `GPU_MAX_HW_QUEUES=16` is -8 % more on prefill
   and **+8 % on GLM decode, so it is not for the service**; with the routed-expert kernels skipped the
   prefill would be -25 % (an upper bound for a better expert chunk kernel, ~2.2 ms a token on the
   critical path). The staged DMA reaches 21 GB/s aggregate (27 without the expert kernels) against
   M4's 52; **the host source (144 GB of 4 KB-page pinned mirror), its span, flags, copy size, number
   of streams, hardware-queue count, ring size (400 MB to 1.2 GB: flat) and generic compute
   contention are all exonerated**; a replay of the engine's own copy lists with the ring's events
   runs at 57 GB/s. **Open: a factor ~2 in what the engine does beside the copies.**
   [§L5-GLM-TIMELINE, §L5-GLM-EMBED, §M7-HOSTSRC]
2. **DeepSeek: do not set `FRANKEN_HIP_GRAPH=1` with `FRANKEN_ADAPT=1`.** Any two of adaptation,
   the staged miss path and graph replay are fine; all three are 51 -> 92 ms. The service runs
   eager. Rev 71's "the 89-102 ms was the wrong placement" is corrected. Mechanism not isolated
   (the router atomics are exonerated, swaps and ticks are not needed). [§DS4-ADAPT-GRAPH]
3. **Card 0's slow small GEMVs are not the card**: a microbenchmark reads 145-147 GB/s on all three
   (`follows=none`); the engine's dev0 is 83:00.0 (confirmed). The deficit is something dev0 does in
   the real token. [§M6-SMALLGEMV]
4. **Layer lookahead STEP0 (review point 2):** one layer ahead predicts 57 % (8k prose) to 70 % (chat)
   of GLM's routed experts and covers 55-60 % of the missed bytes at ~1.15x the traffic (k = 8);
   previous-token reuse covers 13 %. Positive, modest; ~2 bytes cross for every useful one. Not
   adopted; STEP1 would be a decode-side prefetch A,B,B,A. [§L4-LOOKAHEAD-STEP0]
5. **Qwen3.8 MTP (review point 3) is blocked at STEP0:** the served UD-IQ4_XS GGUF has no `mtp` tensors;
   the FP8 checkpoint has a one-layer `mtp.*` head. Projected (arithmetic, not measured) ceiling about
   +30 % at 60 % acceptance (trunk ~5 GB shared across two tokens, experts ~1.2 GB each). Needs a
   conversion of the head and a draft path; not started.

## 6. How to run things (what bit this session)

- Everything from `HANDOFF-2026-09-26.md` §5 still holds. New: **foreground `sleep` is blocked in this
  harness**; use `Monitor` with an until-loop, or a backgrounded `until` loop that exits when the chain's
  process is gone, and arm it BEFORE leaving the launch. Watchers expire after 30 minutes.
- Queue chains with a tiny sequencer (`seq_*.sh` pattern: wait for the previous one's process to go
  away, then `run_chain.sh` it, retrying on rc 3) so the rig is not idle between turns. Those scripts
  are not in the repo (they are 10-line wrappers); the chain scripts they launch are.
- Qwen's `franken_decode` exits **rc 4** on the plain decode command; the baseline chain's preflight maps
  it to success. A chain that counts non-zero exits will report `failures=N` for Qwen runs: read the
  verdict lines, not the exit status.
- `glm5_gpu_gate.sh` and `ds4_gpu_gate.sh` still print a verdict on stdout and a different exit status
  (see §BASELINE-7.0.0-38-DS4-GLM); `ds4_gpu_gate.sh` still points at the removed `~/src/colibri-m1`;
  `ckpt1006/ds4_shared_gate_chain.sh` carries the commands with the paths replaced.
- 40 GB `hipHostMalloc` pools take ~25-30 s each to pin and fill (1.3-1.7 GB/s): a benchmark that
  allocates per arm (M4) takes 12x longer with a 40 GB pool; the transfers are not slower.
- An agent may not start a GPU binary; two agents' CPU checks overlapped chains this session and had to
  be reported. Tell them to check `~/bench/.rig.lock` first and to wait.
