# V1 step 0: a Vulkan expert tier for `qwen36` — reading report (Sonnet, 2026-09-16)

No rig, no build, no code change. This document is the reading FRANKEN-ENGINE-PLAN-2026-09-15.md
§2.6 (V1, H2b) asked for: what the CUDA tier's contract actually is, what
`qwen38-vk`/`glm53` already do that V1 can copy verbatim, and where the two
diverge. Every claim below cites `file:line` against the tree on
`perf/franken-v1-step0` (based on `perf/context-matrix-64ki`, commit
`116d2f5`). Written for an Opus-tier engineer doing steps 1–2; nothing here
needs re-reading to start.

## (a) The open question, answered: gs64 group scales, not just per-row

**The CUDA tier takes gs64 (or any configured) group scales. It is not
restricted to per-row `gs/us/ds`.** The evidence, end to end:

1. **The container tells the engine its group size.** `qwen36_meta.json`'s
   `expert_gs` field is read into `Cfg.expert_gs` (`c/qwen36.c:602,1189`) and
   cached in `g_expert_gs` (`c/qwen36.c:957,2880-2881`). The gs64 container
   (`Kreuzzelg/qwen36-35b-a3b-colibri-i4-gs64`, `docs/qwen36.md:19-20`) sets
   this to 64; the per-row container leaves it 0.
2. **The scale array is already shaped for groups, on the CPU side too.**
   `scale_count_gu`/`scale_count_d` (`c/qwen36.c:1397-1398`) compute
   `inter * ceil(hidden/expert_gs)` and `hidden * ceil(inter/expert_gs)` when
   `expert_gs>0`, else the per-row count (`inter`/`hidden`). This is the same
   array the CPU kernel `matmul_q_gs` consumes (`c/qwen36.c:1003`) and the
   same array `qt_note`'s `gs/us/ds` parameters carry
   (`c/qwen36_tier.h:92-94`).
3. **`qt_init` takes the group size as a first-class argument and sizes its
   own scale buffers identically.** `qt_init(..., int expert_gs, int
   expert_is_int4)` (`c/qwen36_tier.h:83-85`, called at `c/qwen36.c:2953-2954`
   with `m.c.expert_gs`). Inside, `G.sc_gu`/`G.sc_d` are computed with the
   *exact same* `ceil(dim/expert_gs)` formula (`c/qwen36_tier.c:552-553`) —
   not derived independently, so there is no place for the two sides to
   disagree on layout.
4. **The upload path dispatches to a grouped-int4 Vulkan-style tensor format
   when `G.egs` (the cached `expert_gs`) is set**, calling
   `coli_cuda_tensor_upload_g(&tg, ..., fmt=4, ..., G.egs)` for gate/up/down
   (`c/qwen36_tier.c:188-191`) — a *different* call than the per-row path
   (`coli_cuda_tensor_upload(..., fmt=2, ...)`, `c/qwen36_tier.c:192-195`).
   fmt=4 is "grouped int4" throughout this codebase (see (d)); fmt=2 is
   plain per-row int4.
5. **The device kernel actually indexes by group, not by row.**
   `absorb_scale(...)` (`c/backend_cuda.cu:326-331`): for `fmt==4`,
   `g = k / gs; return wscale[row*ng + g]` — a genuine per-group dequant,
   documented as mirroring `quant_matmul`'s own fmt==4 branch. This is not a
   per-row shim wearing a group-size parameter; the group index is read from
   the input position `k`.
6. **int8 with grouped scales is explicitly refused** (fmt=1, i.e. non-int4,
   cannot express groups): `c/qwen36_tier.c:540-544`, `"int8 experts with
   grouped scales (gs=%d) cannot be expressed on the GPU (fmt=1 is per-row
   only) -> CPU path"`. This refusal is irrelevant to V1: the gs64 container
   is int4, format 4, which is exactly what group scales are for.

**Conclusion: V1 serves the gs64 container
(`Kreuzzelg/qwen36-35b-a3b-colibri-i4-gs64`) unmodified.** Nothing in the
tier contract, the CUDA kernel, or (per (d) below) the Vulkan shaders needs
to change to accept it — the whole path from container → `Cfg.expert_gs` →
`qt_init`/`qt_note` → `fmt=4` upload → grouped dequant already exists and is
exercised today by the CUDA tier. Per-row int4 (`expert_gs=0`,
`Kreuzzelg/qwen36-35b-a3b-colibri-i4`) also works unchanged (it is simply the
`expert_gs==0` branch of the same formulas). The only container variant the
tier cannot express on a GPU is int8-with-groups, which nobody ships for
this model (`docs/qwen36.md:71-79` recommends gs64 over per-row int4
specifically for int4; int8 has no such option in this codebase).

## (b) The `qt_*` contract

Declared in `c/qwen36_tier.h`; compiled under `COLI_CUDA` (implementation in
`c/qwen36_tier.c`), else the inline no-op stubs at `c/qwen36_tier.h:119-142`
keep the CPU-only engine's call sites valid with zero overhead.

**Init / teardown (called once, off the per-token hot path):**
- `qt_init(n_layers, n_experts, hidden, inter, cap_experts_per_layer, topk,
  expert_gs, expert_is_int4) -> bool` (`h:83-85`, impl `c/qwen36_tier.c:474`).
  Requires `cap == n_experts` (full RAM residency; enforced at
  `qwen36_tier.c:478-481`) except in fp8-streaming mode. Owns device
  selection (`COLI_GPUS`/`COLI_GPU`), CUDA context init, per-device VRAM
  budgeting (`CUDA_EXPERT_GB`), `HEAT_FILE` load, and spawns the background
  uploader thread. Blocking; runs once at startup.
- `qt_init_fp8(...)` — Qwen3.8's streaming variant (`h:81-82`, not used by
  `qwen36`; documented here only because it shares the file).
- `qt_ready() -> bool` — cheap poll of `G.on`, called every token to pick
  the tiered vs. plain MoE path (`c/qwen36.c:1912`, also `1516`, `2372`).
- `qt_shutdown()` — registered via `atexit` (`c/qwen36.c:2956`); joins the
  uploader thread, persists `HEAT_FILE`, calls `coli_cuda_shutdown()`.
- `qt_stats()` — one stderr telemetry block, called once at the end of a run
  (`c/qwen36.c:3085`).

**Placement table (init-time, called per layer during setup, not per
token):**
- `qt_place_of(component, layer) -> device|CPU`, `qt_trunk_offer(component,
  layer, bytes)`, `qt_lmhead_init/matmul`, `qt_dnproj_init/matmul` — the R4
  trunk-placement mechanism (`h:36-74`). `qt_dnproj_matmul` (`c/qwen36.c:2081`)
  and `qt_lmhead_matmul` (`c/qwen36.c:2274`) *are* on the hot path (once per
  DeltaNet layer / once per token respectively) but are placement, not
  expert routing — **V1's scope per the plan is the expert tier; the trunk
  placement is a separate, already-CUDA-only mechanism that would need its
  own port if wanted, and nothing in the plan asks for it.**

**Per-token hot path (the MoE expert loop, `c/qwen36.c:1963-2009` and the
pilot lookahead at `2372-2375`):**
- `qt_note(layer, eid, g4, u4, d4, gs, us, ds)` — non-blocking; "here are
  this expert's RAM pointers, bump its heat, maybe enqueue an async
  upload." Called once per selected expert per token (`c/qwen36.c:1969`) and
  once per lookahead candidate from the next-layer pilot thread
  (`c/qwen36.c:2374`). **Ownership: the tier does NOT copy these pointers
  synchronously in the normal (non-streaming) mode** — it stores the raw RAM
  pointer (`if(!s->g4){ s->g4=g4; ...}`, `qwen36_tier.c:826`) and only
  copies bytes later, inside the uploader thread, when it dequeues the
  staged entry (`stage()`, `qwen36_tier.c:67-87`, called at line 774 while
  still under `G.mx`). This is why `cap==n_experts` is required: the RAM
  slot behind that pointer must never be evicted for the pointer to still be
  valid whenever the uploader gets to it.
- `qt_issue(layer, eids[K], K, x) -> bitmask` — async: for every resident
  expert among the K selected, launch its GPU expert-group compute and
  return without waiting (`qwen36_tier.c:979-1013`, one
  `coli_cuda_expert_group_issue` call per device that has hits, looping
  `for(di<G.ndev)`). Non-blocking; the caller (`c/qwen36.c:1972`) then
  computes CPU misses (unmasked k's) and the shared expert *while the GPU
  groups run*, exactly the overlap G9 already does for `glm53`
  (`c/qwen36.c:1974-2003`).
- `qt_take(mask, val[K], K, out[hidden])` — blocking: waits on each
  device's fence, accumulates `val[k]*y_k` into `out` (`qwen36_tier.c:1015-
  1034`, called at `c/qwen36.c:2005`). Must be called exactly once per
  `qt_issue` (`G.issue_open` guards a second concurrent issue,
  `qwen36_tier.c:989`, `1031`).
- `qt_is_resident(layer, eid)` — used only to decide whether the RAM int8
  copy of an expert can be freed (`c/qwen36.c` warmstart path via
  `slot_ensure_int8`, `c/qwen36.c:1554` docstring); not itself in the
  decode loop.

**Warmstart (init-time, potentially long-running, off the token loop):**
- `qt_plan_fill(layers[], eids[], max) -> count` — reserves budget for the
  heat-ordered fill set without loading (`qwen36_tier.c:884-909`), called
  once from `tier_warmstart` (`c/qwen36.c:2754`).
- `qt_note_planned(layer, eid, g4,u4,d4, gs,us,ds)` — thread-safe, callable
  from any number of parallel loader threads (`c/qwen36.c:2762` `#pragma omp
  parallel for`, call at `2778`); stages and enqueues one reserved expert;
  blocks only when the upload queue is full.
- `qt_note_block(...)` / `qt_fill_next(...)` — a second, non-parallel
  warmstart shape declared in the header (`h:104-110,114`) that `qwen36.c`
  does **not** call today (the engine uses `qt_plan_fill` +
  `qt_note_planned` exclusively, per the grep in step 3 below); keep them
  wired the same way for a Vulkan tier or drop them, but note the asymmetry
  if dropping — the header contract is wider than what `qwen36.c` exercises.
- `qt_fill_wait()` — blocks until the upload queue drains
  (`c/qwen36.c:2794`).

**28 `qt_` occurrences in `qwen36.c`** (`grep -n "qt_" c/qwen36.c`): 20 are
live function calls (listed above by role), the rest are the `extern double
g_qt_iss/g_qt_cpu/g_qt_tak` phase timers and comments referencing the tier.
Every call site is guarded by `qt_ready()` or is itself a no-op under the
`COLI_CUDA`-less stub, so none of them move when V1 adds a Vulkan
implementation behind the same symbols — **the 28 call sites do not move**,
exactly as the plan requires.

**What is CUDA-specific and leaks through the contract:**
- The RAM-pointer-retention model (`qt_note` storing raw pointers, not
  copying) assumes a single async upload queue with one dedicated uploader
  thread and a staging `malloc`/`memcpy`/`free` per entry
  (`qwen36_tier.c:756-780`) — backend-agnostic in principle (it is plain
  pthreads), but every call *inside* that thread
  (`coli_cuda_tensor_upload[_g]`, `coli_cuda_init`, `coli_cuda_mem_info`) is
  CUDA. A Vulkan port keeps the queue/thread/heat/LFRU machinery
  (`qwen36_tier.c:1-473`, `700-978` — none of it mentions CUDA types beyond
  `ColiCudaTensor*` and the handful of `coli_cuda_*` calls) and swaps only
  the marked calls for `coli_vk_*` equivalents.
- `qt_issue`/`qt_take`'s per-device loop (`for(di<G.ndev)`) assumes an
  **arbitrary device count** reached through one generic
  `coli_cuda_expert_group_issue(tensors, ..., device-implied-by-tensor)`
  call per device. Vulkan's equivalent API is **three fixed functions**
  (`coli_vk_expert_group_issue`/`_issue2`/`_issue3`, one per hard-coded
  device slot — see (c)), not one function parameterised by device index.
  This is the one real shape mismatch in the port.
- `qt_take`'s CUDA form returns a **pointer** into device-mapped host memory
  (`coli_cuda_expert_group_take(device) -> const float*`,
  `backend_cuda.cu:2175`); Vulkan's `coli_vk_expert_group_take(float *y)`
  instead **copies into a caller-supplied buffer**
  (`backend_vulkan.c:1328-1345`, `memcpy(y, G.eg_y.ptr, ...)`). A Vulkan
  `qt_take` needs a small scratch buffer per device rather than a raw
  pointer alias.
- No streams, no pinned-host-memory API is exposed through `qt_*` itself
  (the tier's own staging buffers are plain `malloc`, `qwen36_tier.c:770`);
  that is internal to `qwen36_tier.c`, not part of the contract, so it is
  free to change with the backend.

## (d) Shaders: no new shader is needed

The existing Vulkan expert kernels already consume packed int4 in the
`g4/u4/d4` layout with gs64 group scales — **this is not a hypothetical
compatibility, it is what `glm53` runs in production today** on the same
container convention (int4-g64):

- `c/shaders/qmatmul_gate_up.comp:98-107` (the fused gate+up MoE kernel):
  `fmt==4` branch computes `ng = ceil(I/gs)`, decodes 8 signed nibbles per
  32-bit word (`i4()`, line 33: `((w>>l*4)&0xf)-8` — two's-complement, no
  XOR), and multiplies by `gscale[o*ng + i0/gs]` — a genuine per-group
  scale lookup, group size taken from the push constant `p.gs` (line 27:
  "fmt=4 group size (multiple of 8; host gates otherwise)").
- `c/shaders/qmatmul_tile.comp:81-103` and
  `c/shaders/qmatmul_gate_up_tile.comp:60-69` (the S-row tiled variants,
  relevant to prefill and to X1's retained-command-buffer target): same
  `fmt==4`, same `ng = ceil(I/gs)` / `sc = scale[sb + i0/gs]` pattern.
- `glm53.c` already drives exactly this path for its own int4-g64 experts
  (`glm53.c:2719-2721,2758-2760,2780-2782`, `gate.fmt=4, gate.gs=64` set at
  `glm53.c:780,896`), and `backend_vulkan.c`'s `coli_vk_tensor_ensure*`
  family (`:930,1592,1956`) takes `fmt`/`grp` as plain integer parameters —
  nothing engine-specific in the upload or the kernel.

Since `qmatmul_gate_up.comp` and the tiled variants take `I`/`O`/`gs` as
push constants rather than compile-time shapes, Qwen3.6's hidden/inter
dimensions (different from GLM's) need no shader change either — the
kernel is dimension-generic by construction. **No shader variant is needed
for V1**, provided qwen36's on-disk scale layout matches what the shader
expects: `scale[o * ceil(I/gs) + group]`, which it does — this is exactly
what `scale_count_gu`/`scale_count_d` (`c/qwen36.c:1397-1398`) produce and
what the CUDA tier already uploads unchanged (see (a), point 4-5).

**The one caveat is the nibble convention, already covered in (c):**
qwen36's RAM copy of `g4/u4/d4` is signed two's-complement nibbles
(`c/qwen36.c:1472-1473`, matching `qmatmul_gate_up.comp`'s `i4()`), but the
CUDA tier's `stage()` XORs to offset-binary before upload
(`qwen36_tier.c:66,79-82`) because CUDA's fmt=2/4 kernel path wants that
encoding (`backend_cuda.cu`'s `weight_at`, fmt==2||4 branch, reads the raw
nibble and does NOT XOR — worth Opus double-checking at build time, but the
comment at `qwen36_tier.c:65` is explicit that XOR is "the upload format of
backend_cuda fmt=2"). **A Vulkan V1 must NOT reuse `stage()`'s XOR step
verbatim** — it should upload the signed nibbles as-is, matching how
`glm53.c` hands its own signed `q4` bytes straight to
`coli_vk_tensor_ensure` (`glm53.c:2719`, no repack visible before the call).
This is a real, small, correctness-relevant difference to flag for
whoever writes the staging function, not a shader problem.

**Swiglu clamp:** GLM's routed-expert GPU kernel is documented (CLAUDE.md,
"The machine and its traps") as skipping `swiglu_limit=10.0`, which its CPU
path applies (`glm53.c:1037` `swiglu_clamped`, `c->swiglu_limit` from config
default 10.0 at `glm53.c:287`). **`qwen36` has no clamp anywhere, CPU or
GPU.** `grep -n "swiglu|clamp" c/qwen36.c` returns nothing; both the tiered
and untiered MoE branches compute unclamped `silu(gv)*u[i]` directly
(`c/qwen36.c:1980`, `2016`, and the shared expert at `1882`), and
`qmatmul_gate_up.comp:134` likewise computes `(gt/(1+exp(-gt)))*ut` with no
bound in any `fmt` branch. **This means V1 does not inherit GLM's
correctness gap**: tier-on and tier-off already compute the identical
(unclamped) swiglu on both qwen36's CPU and the Vulkan kernel it would
share with GLM, so there is no GPU-vs-CPU swiglu divergence to gate on for
step 1's bit-identity requirement, unlike GLM's known, unresolved gap.

## (e) Step list

**Step 1 (Opus) — tier off, bit-identical.** Land the Makefile target and
the skeleton `qt_*` implementation gated by a new macro, without wiring any
real Vulkan compute yet (or with it present but never selected), so the
tier-off path is provably the same binary behaviour as today.
- File touches: `c/Makefile` — add a `qwen36-vk$(EXE)` target mirroring
  `qwen38-vk$(EXE)` (`c/Makefile:1051-1052`): `$(CC) $(NOCUDA_CFLAGS)
  -DQ36_VK_TIER qwen36.c qwen36_tier.c $(VK_OBJ) -o qwen36-vk$(EXE)
  $(NOCUDA_LDFLAGS)`, depending on `qwen36_tier.h qwen36_tier.c $(VK_OBJ)
  $(VK_SPV)` the same way `qwen38-vk` does. `c/qwen36_tier.h` — widen the
  `#ifdef COLI_CUDA` guard to `#if defined(COLI_CUDA) || defined(Q36_VK_TIER)`
  (or add a parallel `#elif defined(Q36_VK_TIER)` block with identical
  prototypes) so the same 28 call sites in `qwen36.c` compile unchanged
  against a Vulkan-backed `qwen36_tier.c`. `c/qwen36_tier.c` — behind
  `#ifdef Q36_VK_TIER`, replace the `coli_cuda_*` calls named in (c) with
  `coli_vk_*` calls; keep every backend-agnostic structure (`QSlot`, the
  upload queue, LFRU, heat) untouched.
  - Env knobs, following the existing convention: reuse `COLI_CUDA`'s role
    with a Vulkan-appropriate name — e.g. `COLI_VK_EXPERTS3=<n>` for the cap
    on qwen36's single expert device (mirroring `glm53`'s

## (f) Risks and what is genuinely unknown until the rig is used

- **`dev_alloc_footprint`'s cudaMalloc-granularity curve is CUDA-specific
  and unmeasured on Vulkan/RADV.** Whether `vkAllocateMemory` rounds
  similarly (and whether it matters at ~20 GB against a 24–25 GB card,
  where `glm53`'s G6 reserve is 1.0 GB) is a rig question, not a reading
  one. If the granularity waste is comparable to CUDA's measured 22–28%
  (`qwen36_tier.c:564`), a naive byte-accounted budget could overshoot and
  hit the same "planned but never promoted" failure class G6 fixed for
  `glm53` (#1331's shape, different backend).
- **The nibble-XOR difference in (c)/(d) is inferred from reading two
  kernels' comments, not from running both and diffing.** `qwen36_tier.c:65`
  says the XOR is specifically for `backend_cuda fmt=2`'s upload
  convention; `qmatmul_gate_up.comp`'s `i4()` decode and `glm53.c`'s direct
  `q4` hand-off strongly suggest Vulkan wants signed nibbles as stored, but
  this should be a one-token oracle check (dump post-dequant floats for a
  handful of weights, compare CPU vs. staged-for-GPU) before step 2 trusts
  it silently, since a wrong nibble convention is exactly the kind of bug
  that passes a coarse "runs and looks plausible" check and fails
  `teacher_forcing`.
- **Single-device assumption may not hold once real VRAM numbers are in.**
  ~20 GB of packed int4 experts is the plan's own estimate
  (`FRANKEN-ENGINE-PLAN-2026-09-15.md:82`); dev3's exact free VRAM after
  driver/other-process overhead, and whether the 20 GB estimate holds for
  the *actual* gs64 container (not just its constituent tensor sizes), is
  unmeasured. If it does not fit with the G6-style 1.0 GB reserve on one
  card, step 2's "all 256×40 on ONE card" premise needs revisiting before
  any gate is run, not after.
- **The qwen36 C test count and pass state must be re-verified at build
  time, not assumed from this document or from CLAUDE.md.** CLAUDE.md
  itself flags this exact failure mode for qwen38 ("there are SEVEN, not
  four" — a stale count was carried forward across sessions); qwen36 has at
  least eight `test_qwen36_tier_*`/`test_qwen36_*` targets in the Makefile
  today (`c/Makefile:1084-1099,1318,1680-1725`) and step 1's gate must run
  whatever that count actually is when step 1 starts, not a number copied
  from this document.
- **X2 (the KL oracle) may not exist yet when step 2 is ready.** The plan
  sequences it as a separate, lower-effort item (§4 rank 2, Sonnet); if
  step 2 lands first, the fallback oracle (`teacher_forcing` + last-token
  cosine) is weaker than what GLM's own gates (G14, G15) used to catch a
  real correctness regression, and that gap should be stated in step 2's
  commit body, not silently accepted.

- `c/tools/convert_qwen36.py:113`: `"The engine (c/qwen36.c) currently reads
  ebits>=5 (int8); the int4 path is WIP."` — false today. `qwen36.c` detects
  and reads true packed int4 by on-disk size
  (`c/qwen36.c:1493-1499,1539-1548`) and has done so since at least the int4
  unpack work referenced in `git log` (`8f44422` "Merge ... upstream/qwen36-
  int4-unpack", `2e7dfa6` "qwen36: vectorise the int4 expert unpack (2.10x
  CPU decode)"). `docs/qwen36.md` itself does not repeat this claim and in
  fact recommends the int4-gs64 container as the primary quickstart path
  (`docs/qwen36.md:14-30`) — only the Python tool's docstring is behind.
- `c/qwen36.c:64`: `#include "qwen36_tier.h"   /* optional transparent
  Vulkan compute backend for MoE experts */` — the header it includes is
  compiled under `COLI_CUDA` only (`c/qwen36_tier.h:24`); there is no Vulkan
  backend behind it today. Likely written aspirationally or copy-pasted
  from a different engine's comment.

  result is "Used to pick the Vulkan pipeline at init time" — there is no
  Vulkan pipeline selection anywhere in `qwen36.c` today (confirmed by
  `grep -in vulkan c/qwen36.c`, whose only other hits are an unrelated local
  variable named `vk_idx` at `c/qwen36.c:2118-2120`, an attention head-repeat
  index, not Vulkan). Both this and the `c/qwen36.c:64` comment appear to be
  from the same aspirational pass and are two more data points for "V1 is a
  real port, not wiring up something that already exists" — consistent
  with the plan's Rev 2 correction.

Two mismatches found overall for shaders/contract: (1) the fmt=4 nibble
encoding (offset-binary XOR in the CUDA `stage()` vs. signed two's-complement
